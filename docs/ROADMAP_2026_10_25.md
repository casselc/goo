## Product direction

Goo helps an engineer see what is happening, isolate a population of interest,
follow evidence across signals, and make the question and explanation reusable.
Start with compact live observations. Reveal scoping, comparison, definition and
evidence actions through interaction. Ordinary OTel data from any application
language must be useful without a goo manifest or sample application.

Keep the Go semantic core, explicit source adapters and framework-neutral passive
components. Definitions, transient observations, immutable captures and authored
investigations have different purposes. A cohesive interface should make those
purposes understandable without merging their authority or clocks.

## What changed in this review

The previous persistence-first suggestion is **replaced**. Existing saving,
immutable evidence, annotations and reusable definitions are substantial. The
bigger next opportunities are general-purpose adoption and a clearer operational
question: which services and resources need attention, what workload am I observing, and
where should I look next?

Three source-backed findings change the order:

1. At the review baseline, startup required prepared/sample configuration even
   for generic exploration. The delivered [generic profile](GENERIC_STARTUP.md)
   removes that dependency explicitly while retaining lab mode; it does not install
   a collector, change source schemas or establish production readiness.
2. Service defaults deliberately summarize mixed span kinds. HTTP/messaging
   native capabilities already exist; the missing piece is an explicit named
   observation population and relevant defaults, not another metrics engine.
3. Rich local verification is not the default CI baseline. The API workflow does
   not run all root Go/Node tests, and its wire-test selection omits the new
   trace-search suite. Bounded output also does not bound full-source scan cost.

These are adoption/coverage/contract findings. This source-and-document review
ran no new browser, performance, source integration or deployment campaign and
establishes no new throughput or production-readiness claim.

## Gates that travel with the work

- **G1 verification:** distinguish default fast checks, opt-in integrations and
  tool-dependent checks. Preserve independent semantic/source/custody oracles.
  Add generated schedules where a shared race owner changes; finite observed
  Quint replay is not exhaustive model checking. No fixed 300-example/80-control
  quota. Keep reproducible compact receipts and current affected frames.
- **G2 reproducibility:** pin the nested verification/instrumentation toolchain
  and sibling dependencies; maintain one thin clean-lab/restart journey spanning
  ordinary OTel entry, service scoping, inspection and existing evidence reopen.
  Reuse that spine rather than repeating the entire product for every change.
- **G3 cost and effects:** record issued source reads, SQL size and representative
  small/larger-cardinality behavior for touched workflows. Inventory GET/POST,
  source-bearing captures and streaming separately against admission/cancellation
  policy. Fix confirmed gaps in explicit slices with compatibility tests; do not
  put SSE under an ordinary request lifetime or raise limits to hide a refusal.
- **G4 product coherence:** validate the whole task on desktop/mobile and keyboard,
  not only a cropped component. Reuse compact scope, table, field, comparison and
  inspector presenters; remove duplicate controls only after task parity. Exact
  provenance belongs in concise disclosure, not repeated boilerplate above data.

These gates support the finite cuts; they are not four additional feature suites
that must all be completed before any useful work can ship.

## Relevant later work and explicit prerequisites

| Candidate | Required next decision or evidence |
| --- | --- |
| High-cardinality facets | Define a separate exact top-K/remainder/denominator contract and real ClickHouse cost evidence. The current full-group refusal is correct; truncated groups must not enter complete-cohort APIs. |
| Collector/exporter diagnostics | First establish one actual instrument source, full identity/unit/temporality and an induced failure signal. If unavailable, stop at the contract/source gap; no decorative health badge. Can be prioritized separately when the source is ready. |
| Exact trace-search/comparison evidence | Choose a concrete preservation task, typed server-held promotion/idempotency and byte/lifetime budgets. Search responses can reach 8 MiB while the existing observation pool permits 2 MiB per entry. Reuse stored raw captures before adding a paired-result store. |
| Saved trace visualization | Source-free rendering of already-held stored pages is a smaller candidate than a new persistent comparison format. A fresh Expand trace must remain distinct. |
| Runtime admission expansion | Review known effect-policy gaps, separate stream/read/publication budgets and compatibility before a shared deployment. An explicit route inventory is not authentication. |
| Float/unit/transform expansion | One concrete unsupported instrument or calculation, explicit numerical semantics and Go/reference/source parity. Existing typed numeric and native families are already delivered. |
| Portability/IaC | Report supported translation capabilities first. New raw-source lowering or CEL/KCL execution needs an actual authoring task; live Databricks needs an execution environment. No incidental DataFusion or language/framework migration. |
| Training/annotation exports | A real consumer and label vocabulary, pinned membership/time/correction basis and leakage policy. Existing tags/reviews are not automatically training labels. |
| Shared collaboration | Authored identity, ownership/concurrency/conflict policy and a deployment target. Existing immutable branches are not a multiplayer editing protocol. |
| Production/shared deployment | Named target, authentication/authorization, tenancy, quotas, retention/backup and restore acceptance. Loopback lab credentials are not a production design. |
| Durable live replay | An actual ingestion/cursor/replay contract; current rolling event-time polling does not establish it. |
| Scheduled alerting/SLOs | Durable evaluation/scheduling, unknown/error policy and notification ownership. Existing on-demand previews do not implement an alert service. |

Keep RUM/session replay, profiling, a generic dashboard builder, multiplayer canvas,
advanced trace path/negative-existence operators and a mandatory bitemporal backend
outside this finite round. They remain possible product directions, not items to
silently accumulate onto the next UI increment.

## Review inputs and resolution

Six independent agents reviewed baseline `9e07b88`. Their recommendations are
inputs to this single queue, not separately approved backlogs.

| Review | Main contribution |
| --- | --- |
| [Product](WHOLE_PRODUCT_PRODUCT_REVIEW_2026_10_25.md) | Service grain and native-to-record incident paths outrank blanket new persistence. |
| [Architecture](WHOLE_PRODUCT_ARCHITECTURE_REVIEW_2026_10_25.md) | Generic bootstrap, explicit lenses, narrow aggregate reads and separate high-cardinality semantics. |
| [Usability](WHOLE_PRODUCT_USABILITY_REVIEW_2026_10_25.md) | Contextual action consistency, answer-first composition and whole-task evidence across surfaces. |
| [Platform](WHOLE_PRODUCT_PLATFORM_REVIEW_2026_10_25.md) | Reuse existing OTel/native profiles; remove demo startup dependencies; make admission/portability/deployment gates explicit. |
| [Verification](WHOLE_PRODUCT_VERIFICATION_REVIEW_2026_10_25.md) | Broaden routine gates and reproducibility; spend verification effort by risk rather than ceremonial counts. |
| [Planning reconciliation](WHOLE_PRODUCT_PLANNING_REVIEW_2026_10_25.md) | Separate parallel enablers from functional order, retire delivered proposals and keep request reuse distinct from result custody. |

Resolution: retain product's service-first user outcome, architecture/platform's
startup enabler and measured read seam, usability's task-level consolidation, and
verification's routine safety net. Automatic operational dashboards are the main product initiative; the HTTP
observation lens is its first vertical slice. Native interval continuation
supports those dashboards and precedes blanket trace preservation. High-cardinality summaries, pipeline diagnostics and observed
result custody have meaningful prerequisites and remain separate decisions.
