# Whole-product verification review — 2026-10-25

## Decision

Keep Goo's independent semantic and real-source verification. Stop treating a new journey, formal model, large property count and dozens of corruptions as a mandatory bundle for every feature. The next verification investment should make the existing evidence reproducible and continuously exercised, then cover a few shared failure boundaries. Another round of feature-specific evidence accumulation is lower value.

This is a source/document review at `9e07b88`, including the delivered trace-search milestone. No tests, builds, browser campaigns, deployments or cleanup were run for this review. Dated outcomes below refer to existing validation records, not newly executed checks. Recommendations are proposed work for the revised roadmap; this document does not authorize deleting tests or evidence.

There is no reason to replace this stack with a single testing framework. Its layers answer different questions. The urgent problem is that the strongest layers are difficult to discover and reproduce together, while the only automated CI workflow is much narrower.

## Highest-value gaps

### 1. Continuously execute the available fast contracts

Make a portable PR gate run root Go tests, the full Node suite and the relevant Python/proxy tests in addition to existing OpenAPI checks. This closes a concrete gap: newly added Go handler suites can currently miss the CI workflow's fixed list. Preserve the existing exact wire fixtures and actual observation checks; do not substitute schema-only testing.

Treat nested modules explicitly. The runtime [go.mod](../go.mod) declares Go 1.24, while [instrumentation](../instrumentation/go.mod) and [verification](../verification/go.mod) require Go 1.27. Native verification additionally has a relative replace for the sibling `observability/quintgo` checkout, npm-installed Quint and Hegel's embedded native library/cache requirements. A fresh worker needs documented, pinned setup for these dependencies, not an assumption that the current workspace layout and caches exist. Add a separate bounded native job after that setup is reproducible. Optional jobs must publish **passed / failed / skipped with reason**, not an undifferentiated green label.

Acceptance: a clean checkout executes a documented fast gate; changed handler/helper tests cannot silently fall outside it; the native job identifies exact sibling/tool revisions and exposes absent live dependencies as skipped. No new browser feature is needed to deliver this.

### 2. Maintain a small integration spine, not a replay of every historical milestone

Create a maintained selection of real lab workflows: ordinary manifest-free OTel → fixed investigation/trace search → explicit trace expansion → capture/reopen with source unavailable → saved-question staging and explicit fresh Run; add the existing Activity pause/return/retained-selection path and one positive XTDB correction/pinned-reopen branch. Reuse delivered journeys instead of rebuilding their semantics. Run the spine on a disposable fresh lab and periodically through process restart. Existing [smoke](../scripts/smoke.py) is useful startup evidence but its successful reservation path does not cover this broader product spine.

A full fresh-checkout integration job is a recommendation, not a claim that it never ran locally. The current validation records contain rebuilt/deployed, restart and optional-store passes; the missing deliverable is a stable automated selection and its reproducible environment. Keep real source parity targeted at changed compiler/source families. API tests already use real HTTP on both sides of the proxy, so extend the remaining [API observation matrix](API_ACCEPTANCE.md#remaining-acceptance) where touched rather than rebuilding all transport tests.

Acceptance: one versioned selection with explicit service/tool requirements, isolated test environments and preserved application volumes; a successful clean-lab run plus a bounded restart/offline-reopen check. Broad authorization, production tenancy, durable business outboxes and power-loss durability remain separate product/architecture work, not assertions that more tests can make true.

Do not make persistence of the newest trace tools the prerequisite for this work. Existing capture/reopen contracts already provide a persistence boundary to exercise. Prefer a useful service/operation investigation that exposes its actual grain, coverage and read effects, then characterize a few full-source plans at two declared lab cardinalities. A bounded trace-ID or witness output does not bound the scan/aggregation cost. Record query latency, source work where available, refusal/timeout behavior and fixture size without treating the current demo or a handler timeout as a production performance guarantee. This is a targeted adoption/read-cost check, not a new benchmarking platform or saved-trace feature.

### 3. Spend generated scheduling on shared race risks

Recent real held-response tests are valuable: they found stale-owner, hidden-control and closed-editor bugs. Repeating an eight-step phase model for each new local action has diminishing returns. Choose one concrete high-risk owner family—request, hold, edit, cancel, leave, return, fresh request—and extend existing generation/driver tooling to vary that schedule against its actual owner implementation. Include response reordering, same-scope replacement and unavailable/known-empty transitions. Keep source/witness arithmetic under independent oracles.

This is a bounded follow-up, not a request for a universal mutable owner or a project-wide model. [The B2 acceptance](QUESTION_PROTOCOL.md) already explains why unlike lifetimes were not collapsed into one generic request owner. Keep actual OTel acceptance separate from controlled-response schedule tests, and label both honestly.

Acceptance: generated alternative schedules drive a real owner, assert effects and scope/revision identity after every action, shrink/reproduce failures, and reject known stale-publication mutants. Do not call fixed observed replay “generated MBT” or require another model for a stateless formatting change.

### 4. Simplify verification code while preserving independent truth

Recent native ledgers reuse earlier private test helpers across families, sometimes through detached adapters for differing body/status/group contracts. This reduced duplication but also produced observer mistakes: display-only `duration_ms`, paged versus complete captures, status normalization and JSON slash escaping are documented in [the verification record](../verification/README.md). A future helper change can affect unrelated historical verifiers.

Extract a small **test-only** contract kit for transport decoding, exact JSON numbers, typed request equality, raw source records, complete stored bytes versus public pages, and effect/cancellation accounting. Give each adapter its own focused tests. Never strip arbitrary fields or rewrite statuses before validating their original meaning. Duplicate span IDs must remain valid raw-record multiplicity where the contract permits them; they are not universal row keys. Hash complete stored bytes/typed payloads from the authoritative representation, not browser-reserialized pages.

Keep arithmetic/set/interval oracles independent and visibly separate from production helpers. Consolidate repeated mechanics, not all expected-value logic. Do not perform a wholesale verifier rewrite merely to obtain a uniform API.

Acceptance: move one repeated boundary used by two real families, preserve accepted fixture results and one meaningful corruption per affected contract, then remove the replaced mechanics. No fresh application traffic or full browser rerun is needed for a proven test-helper-only refactor unless the old observer was wrong about application behavior.

### 5. Make evidence discoverable and portable

[VALIDATION.md](../VALIDATION.md) is approximately 9.6k lines and [verification/README.md](../verification/README.md) approximately 1.9k at this review baseline. They contain useful precise records but also repeat evolving commands, local cache paths, artifact IDs and stage narratives. Local `artifacts/` is [ignored](../.gitignore), so a command referring to an accepted ledger path is not reproducible from a fresh clone without that artifact.

Keep a short current gate index and a compact run manifest: source/deployment identity, tool versions, seed, executed versus skipped checks, fixture definition/hash, accepted ledger references, failure classification and elapsed time. Link historical detail instead of copying it into every status page. Store release/CI artifacts under a controlled retention policy; do not imply that ignored local ledgers are checked-in reusable examples. Preserve replay inputs and a shrunk counterexample for meaningful failures, not only a screenshot of a success.

Acceptance: one current entry point distinguishes commands that work from source alone from commands requiring lab services or retained artifacts; one representative fresh-worker replay retrieves or regenerates its declared inputs. Historical runs remain dated evidence rather than an ever-expanding list of mandatory release gates.

## A bounded acceptance policy

Replace numeric quotas with a risk selection made before implementation:

| Change | Required evidence | Usually unnecessary |
| --- | --- | --- |
| Pure semantic/parser/compiler behavior | Independent boundary/property oracle, appropriate type/namespace/time/overflow cases, targeted source parity when lowering changes | New UI actor or a phase model for a pure function |
| Stateful owner or source/publication boundary | Relevant unit/state tests, one held/error/cancel path, exact read/write effects, selected source journey; generated schedules when the protocol itself changes | Re-running every old milestone or generating another fixed model with the same protocol |
| Capture/storage/identity change | Original bytes/IDs/lineage, corruption/refusal, lost acknowledgement/idempotency where promised, offline reopen/restart appropriate to that store | Hashing a public page as if it were the full stored artifact; importing another store's durability promises |
| Shared passive display | Pure/SSR and pre-definition SPA composition, keyboard/focus/disclosure and one desktop/mobile adoption check | New arithmetic properties, capture creation or source reads solely to refresh an unchanged visual |
| API change | Actual handler/refusal/cancellation/limit tests and schema observations for the touched route, proxy behavior where relevant | Treating an OpenAPI schema as endpoint execution or restarting unrelated services |

For each important invariant, require a positive case and a corruption that actually changes serialized evidence and fails the responsible layer. Keep additional boundary cases where they protect distinct risks. “300 generated examples / 80 controls” is evidence about a particular campaign, not a minimum for the next one or a product-quality score. Counts must identify examples versus state steps versus schedules versus browser snapshots.

After relevant checks pass, rerun only for a changed contract, changed executable source, an unresolved failure or a specifically affected deployment/visual. A CSS-only change should not repeat arithmetic campaigns; a corrected observer should preserve its rejected diagnostic, explain the corrected assumption, and rerun that observer against unchanged evidence. Evaluate latency/memory limits using actual measurements; past test elapsed times are not product performance benchmarks.

## Resource and diagnostic policy

Use one exclusive slot for live browser/actor acceptance and serialize heavy native/Quint/build work when resources are shared. This repository already fixes Playwright to one worker and the [journey wrapper](../scripts/run_journeys.sh) pauses/restores only its owned traffic generator without deleting stale stream entries or volumes. Make that ownership visible in the runner instead of relying on messages between operators. Record genuine environment failures separately from assertion failures; do not cure contention with hidden retries or disabled checks.

Preserve the current [diagnostic retention](DIAGNOSTIC_RETENTION.md) separation: disposable recordings are not application telemetry, captures, investigations, native retained evidence or committed documentation frames. Its implemented soft limit is 512 MiB for eligible raw browser files; successful/failed/unknown TTLs are 24h/7d/72h, with active/pinned protection. It deliberately does not bound logs or compact JSON. Therefore it is not a total disk budget.

Proposed additions: archive one accepted compact evidence set per release/family; retain meaningful first-failure and final-pass summaries plus shrunk reproductions; compress repetitive diagnostic logs; explicitly expire superseded successful scratch bundles. Preserve pinned failures and active producers, and never silently discard an artifact that a current acceptance manifest needs. Any total-artifact policy must be separately designed and tested before use. Avoid global cache/image pruning; preserve known rollback images, application data and durable stores. Budget and toolchain/cache provenance belong in the run manifest. Set provisional fast/integration scheduling budgets only after collecting cold/warm runtime data; do not turn a guessed deadline into flaky correctness acceptance.
