# Saved Activity baseline continuity — architecture 322

Status: final source review accepted; generated execution recorded below.

This depth round lets Activity use an existing typed-policy capture in its two
established baseline tasks. It removes obsolete presentation gates without creating
a new baseline store, source executor or environment representation. The preceding
321 round supplied the broader general-purpose previous-window workflow; subsequent
consolidation should assess real structural/usability/performance friction rather
than extending another profile automatically.

## Distinct authority contracts

Activity latency compares immutable saved duration counts with the current completed
Activity duration read. `activity-baseline.capture` must retain `adoptStoredExplore`
validation, receipt/result scope equality, complete duration partition checks and
stored source basis/clock. Capture/catalog loads and the supplied comparison do not
query telemetry. Removing the selector ban does not allow malformed receipts,
changed partitions or a claimed source witness to enter through a generic element.

Activity explanation instead reuses the saved **question**, then explicitly rereads
both fixed populations. Stored counts are neither input totals nor authority for
that fresh result. Its savedScope validation checks requested receipt identity,
custody time, record question and matching receipt/result scope, plus same signal
and checked environment against the selected side. Saved predicates, namespace and
window remain literal independent operands. Corrupted counts need not invalidate
question-only reuse, but a changed recorded question must refuse.

The existing saved-capture-protocol checkedRecord helper can consolidate the shared
scope equality check. It must retain exact canonical receipt/result identity after
the deliberate removal of inspection offset/limit, not broaden receipt equality to
arbitrary cross-wire representations. Semantic current-only named equivalence is
appropriate only when comparing the two independent operands. Preserve predicate
validation formerly performed by source-snapshots.sameQuestion; full dataset
admission and stored-page constraints remain separate from this scope-only helper.
No circular import from explanation into saved-capture-protocol is needed.

## Navigation and lifecycle

The explanation filter planner already returns a checked question for the chosen
side; the adapter validates signal, environment and exact side bounds. Shared
questionLink supports typed record questions, so the local selector-only refusal
can be removed while retaining those guards. A baseline lead must stage/open its
baseline window, not the current Activity window. Navigation remains intent and
requires explicit telemetry Run.

Retain receipt generation/current-scope/abort checks: a response from an old Activity
scope cannot attach a baseline or overwrite current status. Closing, changing policy
or leaving the surface must retire pending work. Catalog and loaded-reference labels
must show the checked policy, including empty and unreported, rather than a blank
scalar environment. No automatic policy downgrade or source reread is introduced.

## Final source review and generated execution

The shared checkedRecord helper validates both full predicates and record-question
shapes, then compares canonical scope with delivery paging removed. Existing
source snapshot admission still independently checks every dataset and retained
page. This consolidation preserves rather than weakens the old source boundary.
Latency capture no longer adds a redundant equality check that incorrectly treated
inspection paging as a changed population; receipt and returned result remain
exact in all semantic scope fields.

Both obsolete selector bans are removed, checked policy labels replace scalar-only
catalog text, and explanation side links retain side signal/policy/window checks
before using the shared question protocol. Acquisition, cancellation, generation
and active-scope ownership are unchanged. Frozen baseline comparison still supplies
stored totals; explanation still supplies only questions to explicit fresh reads.
No source-authority or persistence change was introduced.

The generated lane uses actual Go Source.Fetch-produced duration datasets over a
bounded fake physical transport, not a handwritten snapshot model. Each case uses
eight existing source reads to build two DTOs. Thirty cases cover typed policies,
namespace presence, independent predicates/windows, equivalent current-only
operand representation, receipt/result mismatch, malformed predicate/partition,
paging-independent question reuse, caller ownership, Go explanation side planning
and JS question links. A fixture initially omitted required selected-row resource
metadata and correctly failed the existing source guard; adding real matching
resource maps and SpanName fixed the fixture, with no production changes. The
first complete corrected run passed in 64.996 seconds under concurrent compilation.
Final execution, including the semantically equivalent cross-wire receipt-change
refusal, passes all 30 generated cases in 12.248 seconds with zero skips. Native and endpoint budgets are recorded
separately in VALIDATION.
