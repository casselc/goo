## Existing path and bounded entry decision

`stream-entry.mjs` already puts Analyze this scope/window, Explain this window,
Errors & exceptions, Log patterns and Build fixed question inside Investigate.
Analyze copies the applied selector and completed source `readWindow`, pauses
Activity and stages a fixed record question through `onOpenFixed`. It preserves a
return anchor. It does not make the loaded rows a full population.

`population-workspace.mjs` already stages an adjacent previous equal-width query
through `CapturedCount.previousQuery` and checked composition. Its Compare previous
window action requires an ordinary Count composition and no facet. The natural
Activity route therefore exists, but a person must discover and configure Count
before finding the comparison action. Explain this window is an existing separate
population-explanation task with a held-observation brush and explicit reread;
it is not a reason to add a second explanation wizard.

First exercise Analyze → Count composition → Compare previous window → Run in
the real app and record the actual discoverability cost. If the gap is confirmed,
consolidate the existing Investigate actions with a compact Compare previous window
entry that stages the existing checked Count composition. Keep it in Investigate,
not a second toolbar or a new picker/wizard. Preserve fixed-record analysis when
it supplies a distinct task. Do not add redundant synonyms for the same operation.

The entry uses the applied selector and last completed read window, copied once
at activation. Preserve signal, typed environment policy, namespace presence and
exact predicates. Dirty/unapplied scope, missing completed window and unavailable
previous bounds need actionable refusal. Never compute bounds again from wall
clock after staging. Selected is [from,to); Previous is [from−width,from), where
width=to−from. Staging pauses and retains Activity; it performs no source read,
comparison request, capture publication or custody write. Run explicitly acquires
the full fixed populations with their actual source-read facts. A buffer length,
Find match count or held time-bin count cannot supply either total.

## Passive operand-role contract

Application adapters already supply Previous window/Selected window, Fixed baseline
window/Selected window, Frozen baseline/Current held, Held parent (overlapping)/
Selected and Rest of parent/Selected. Preserve those exact meanings across the
operand facts, Summary and Groups. Labels describe operand roles; evidence mode,
read basis and custody come from the existing EvidenceScope data independently.
A role string cannot grant stored-snapshot authority.

Source currently drops supplied roles when configuring `goo-measure-comparison`
and `goo-group-count-comparison`. Groups hardcodes Baseline/Current held, while
Summary hardcodes Baseline/Selection. Correct the passive display contract only;
do not add role fields to query, capture or comparison evidence schemas. Generic
standalone components use neutral Operand A/Operand B defaults, without
implying a held owner, a user selection or a receipt. Their exact change is B−A;
real product owners supply the natural task roles above. Keep baseline/selection identity and signed
arithmetic unchanged.

Propagate roles through all the following parallel surfaces:

- Summary column headers, narrow side labels and exact-change disclosure.
- Groups column headers, change tooltip, absent-side descriptions and accessible
  names, plus group-side stage button accessible names and tooltips.
- Operand headings and scope/read facts, without a redundant Baseline prefix
  turning a real supplied role into a contradictory or doubled heading.

Change means Selected window minus Previous window for this task. Rest is not a
frozen baseline; a held overlapping parent is not disjoint; a fixed full source
query is not Activity's held rows. Preserve unavailable/diagnostic/no-data states,
unknown upstream coverage, exact counts and denominators. Existing source-read,
window and custody clocks remain separate. Use literal text rendering and bounded
checked role options, including detached property updates and server attributes.
No extra banner is needed to repair contradictory column names.

## Receipt-baseline owner correction

A second source audit traced `countCurrent()` to `execute()`'s explicit
`/api/explore` acquisition and `prepareCountComparison()`'s separate stored receipt
load. In the population workspace, a receipt baseline therefore means **Frozen
baseline / Selected window**, not Frozen baseline / Current held. The selected
operand remains a freshly acquired full fixed query even when its baseline is an
immutable receipt. Presence of that receipt grants no authority to the other side.
The genuine temporary held owner can retain Current held. Existing fixed/frozen
EvidenceScope modes and read/custody clocks already support this correction.
Root and labels reviewer received this source decision before owner edits.
