## Intended boundary

One optional typed comparison child references one immutable stored capture.
The parent remains the sole query owner. The compared current count comes from
its held whole-population result, never the newest inspection-page count. Capture
preparation reads stored evidence and uses existing pure comparison arithmetic;
it does not query telemetry or create a comparison receipt. Definitions reopen
staged and source-free. Evidence publication still requires separately confirmed
capture and the existing two-capture receipt flow.

The agreed declaration is closed, parent-signal-pinned and count-only, with an
optional bounded title. It adds no query binding language, evidence store or
arbitrary renderer escape hatch. Existing sibling visibility/order controls
remain the layout mechanism.

## Acceptance constraints supplied to implementation

- Validate both original questions. Require one eligible grouping; exclude
  status, numeric/histogram, reported-edge and unsupported pattern/state/time
  profiles. Typed environment policy equality must admit semantically equivalent
  legacy named/current-only representations while preserving policy differences.
- Normalize documented delivery paging, then compare every definition directive
  except fixed windows. Keep both UTC windows and clocks visible. Unequal window
  durations must not turn raw counts into rates or automatic health thresholds.
- Canonical ViewComparison owns exact count changes. Known zero remains a known
  count difference even when its outer envelope says no_data; disagreement
  withholds the change. Do not calculate a replacement JavaScript delta.
- Bind async preparation to generation, chosen capture ID and held selection
  identity. A baseline change withdraws the old pair immediately. Navigation,
  fresh Run, child ownership and reuse retire stale preparation. Paging retains
  the pair because it retains the aggregate owner.
- Reused definitions must recheck baseline compatibility against the destination
  root, or remain explicitly unavailable. A capture selector is never rewritten
  to make a copied presentation work.

## Source disposition

Go declaration/domain review: the comparison role remains one closed typed child,
with an exact immutable ID, parent-pinned scope and count-only display. Optional
title null/unknown fields are explicitly rejected. The pure compatibility helper
validates both original questions, applies checked environment equality and the
existing capture paging normalization, then preserves all definition directives
apart from windows. Composition reuse conservatively refuses changed root
configuration rather than rewriting a baseline selector. No Go source blocker is
identified; focused/full test results belong to the execution owner.

Browser/runtime source review finds no remaining blocker after the following
integration corrections:

- Browser reuse now applies the same conservative source/destination root
  compatibility check as Go, before separately validating the actual baseline.
- Changing a baseline draft immediately removes the passive rendered pair and
  scope/evidence details. Clearing only in-memory pair state had left stale
  evidence visibly attached to a new draft.
- Set/Remove and input/catalog handlers check current connected/visible ownership
  before mutating draft guards. A retired Set cannot clear the current editor's
  pending error merely by being clicked programmatically.
- Pending preparation cannot discard a newly selected record through final
  whole-panel rendering: records are explicitly inert during preparation and
  their application owner rejects programmatic record actions. Existing selected
  records prevent starting preparation. The verifier owns the delayed-read check.
- Baseline response admission verifies the immutable receipt ID matches the
  chosen reference before pure comparison. Async commit also checks source/query
  drafts, selected facets, parent generation, baseline ID and held result identity.

The prepared pair is passive held content: paging changes only the inspection
page; local rendering/order/visibility does not reacquire a baseline. Full Run
replaces the held current result and explicitly prepares a visible configured
baseline. Reopen remains staged and source-free. Canonical comparison owns exact
signed count arithmetic and conservative evidence quality; no display arithmetic
or new receipt family was introduced.

Product source review also moved the existing baseline evidence link into a
visible capture-title line beside the summary. This identifies the chosen human
baseline without expanding the technical scope/custody disclosure or duplicating

## Next bounded capability

The useful next question is **which groups account for the count change?** The
current journey proves operand ownership and total comparison. A single aligned
count breakdown over the already-returned one-field cohort rows would extend the
investigation while reusing the exact pair, capture reference and held basis, with
no additional acquisition. This is preferable to adding summary measures merely
because the renderer can display them.

Propose that small contract before implementation: canonical row/profile support,
shared-scale count geometry and exact values, explicit one-sided/missing/known-zero
groups, and existing quality/independent-window semantics. Add side inspection
only when a typed owning-scope action can stage the precise selected group; do not
reconstruct deltas or selectors inside a display component. Latency, rates and
more general differing-filter contrasts remain later decisions.
