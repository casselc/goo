# Holistic CEL integration: language and extension review

Status: specialist source review, 2026-11-14. Proposed requirements below are not shipped behavior. Scope: checked CEL, predicate IR, package/view authoring, portability and editor contracts. The existing pilot is a sound narrow compiler boundary; it is not yet a general expression language for every existing Goo question.

## Three decisions to make first

1. **P0: define the editable language against the complete existing predicate IR.** `querycel/program.go:declarations` covers fixed columns only. `exploration/model.go:Predicate`, `Field.Type` and `validatePredicate` also admit resource/attribute keys, presence, numeric bindings and derived exception/pattern fields. An editor cannot truthfully offer universal text/visual conversion today. Either explicitly label and capability-check a fixed-field refinement editor, or implement the missing primitives before offering full predicate editing.
2. **P0: separate authored source from normalized execution identity.** The pilot lowers checked overloads into ordinary predicates and discards syntactic distinctions. Keep original source, comments, compiler/library contract and source mapping in an authoring envelope; execute only a successfully validated IR. Define a canonical printer and normalization equivalence before visual edits can replace text. The CLI receipt's original `expression` is useful, but is not a persistent round-trip contract.
3. **P0: specify presence and exact numeric semantics before adding maps or extensions.** Goo's `ne` excludes missing values, numeric states distinguish missing/empty/invalid/valid, and derived exception type can be absent. Ordinary CEL map lookup, `null`, errors and unknowns do not automatically implement those meanings. Never lower an apparently similar expression by dropping its presence guard or converting malformed input to zero.

## What is actually implemented

`querycel/compile.go:Compile` uses checked `cel.dev/cel-go` overload identities, clears macros, admits all subtrees before execution and validates the resulting ordinary predicate. It supports AND/OR, fixed-field string/uint equality, uint inclusive comparisons, literal contains and severity-band equality. Severity lowers to ordinary numeric bounds; library identity is `goo.cel.otel/v1` and overload identity is versioned (`querycel/library.go`). `Program.Apply` clones and validates the whole parent, ANDs the entire parent predicate, preserves query fields and revalidates expanded budgets. This is the right execution boundary.

`Program.Eval` requires every referenced fixed field, including short-circuited references, and canonical uint decimal input. It is a normalized-record reference evaluator, not a missing-tolerant telemetry interpreter. `cmd/goo/plan_cel.go` is a pure file-to-plan CLI with a `goo.cel-plan/1` receipt; no source query, UI editor, generic plugin registration or Databricks record lowering follows from it. `docs/CEL_PREDICATE_PILOT.md` and the leading sections of `VALIDATION.md`/`docs/KNOWN_ISSUES.md` state these limits consistently.

## Coverage and exact failure cases

| Existing concept | Current CEL coverage | Required contract |
| --- | --- | --- |
| Fixed strings/uints and AND/OR | Supported subset | Deterministic literal escaping, uint suffix and grouping |
| Field existence/missing | No admitted syntax | Explicit presence primitive with logical-field semantics |
| Resource/attribute maps | None | Literal keys only initially; presence-aware comparison |
| Numeric bindings | None | Versioned binding type, scale, unit, parse policy; exact state and comparison primitives |
| Derived columns | Incomplete | Versioned symbols for duration/status classes, body pattern and exception identities/states |
| Query measures/projections | Preserved by Apply, not CEL authored | Separate declarative query/measure contract |

Concrete examples:

- `log.severity_number >= 17` fails type checking/admission; `17u` is required. `log.severity_number > 17u` also refuses, although strict comparisons exist for numeric-binding predicates. Do not silently turn this into `>= 17u`; a future rewrite to `>= 18u` must handle uint64 overflow.
- `resource["service.name"] == "worker"` and `has(log.body)` are explicitly rejecting fixtures in `querycel/program_test.go:TestUnsupportedExpressionsRefuseBeforeReferenceExecution`. A fixed field's presence is not nonempty text: `log.body != ""` cannot stand in for `exists`.
- Existing `{field:{kind:attribute,key:route},op:ne,value:"/health"}` matches only present nonmatching routes. For a missing route, Goo returns false. Replacing it with unguarded CEL lookup may error; replacing it with `!(present && equal)` yields true. Both change semantics. Missing-inclusive rest is an explicit OR of missing and ne, as demonstrated by `exploration/numeric_predicate_test.go:TestNumericPredicatePackageAndPopulationComposition`.
- `exploration.NumericBinding{Field: attribute.measure, Type: decimal64, Scale:2, Unit:"ms", Parse:"canonical-decimal"}` with `gte "0.01"` has no current CEL representation. A double literal, `int(...)`, or permissive conversion loses its declared scale/range/state contract. For raw `""`, `"oops"` and absent key, comparisons must remain false, with separate empty/invalid/missing states (`exploration/numeric_binding.go`, `numeric_predicate.go`).
- `span.exception_type == "Timeout"` is undeclared, despite logical `exception_type` existing in `Field.Type`. Its ambiguous/unreported absence must survive lowering. `exception_fingerprint_v1` permits only exact identity/presence predicates and validates fingerprint values; `body_pattern_v1` rejects contains (`exploration/model.go`). Exposing these as arbitrary strings would bypass domain restrictions unless ordinary IR validation remains authoritative.
- `otel.severityBand(log.severity_number) == "error"` and its explicit 17–20 bounds lower to the same predicate shape. The lowered AST cannot tell which spelling, whitespace or comment the author chose. Reversed literal comparisons also lose source orientation. A printer can provide canonical text, not recover original source.
- `false && log.body.matches(".*")` refuses before evaluation. Keep that property: dead branches cannot smuggle unsupported functions or extensions into saved intent.

## P0 grammar and authoring contract before a general editor

Publish a versioned grammar matrix with operations, logical fields, signal, value type, presence behavior and backend capabilities. The initial fixed-field editor may ship independently only if it detects unsupported parents and presents the parent as retained scope with a separately editable refinement. It must never erase unrenderable clauses. Full predicate replacement requires representability of every admitted leaf or explicit refusal before conversion.

Add minimal primitives for presence-aware literal-key attributes/resources, exact numeric binding states/comparisons, and versioned derived-field identity references. Concrete proposed surface forms (not implemented syntax) are `goo.present(resource, "route")`, `goo.missing(resource, "route")`, and a typed binding reference such as `numeric.latency.valid()` / `numeric.latency.gte("0.01")`, where the package declares latency's field/type/scale/unit/parse policy. Prefer closed checked overloads and declarations over an untyped `dyn` expression builder. Exact decimal thresholds can stay strings at the surface only when the checked binding validates them before lowering. Missing and empty remain different.

Do not invent general negation to approximate unsupported operators. General `!` requires a defined domain/error policy and presence-aware complement lowering. Do not equate missing with CEL null. Current fixed inputs have no null or unknown state; a missing required fixed column is malformed input, not a successful predicate result. For maps, specify absent-key behavior explicitly. If unknown/partial activation is later introduced, represent it as an evaluation outcome with provenance; do not convert it to false or healthy. Exceptions in extension evaluation must remain errors.

Define normal form structurally: consistent uint spelling, escaped strings, explicit parentheses, deterministic field symbols, preserved branch order and bounded flattening if chosen. Require `lower(parse(print(N(p)))) == N(p)` for every supported predicate, and idempotent normalization. Normalize fixed uint values such as existing accepted `"01"` carefully: `exploration/numeric_predicate_test.go:TestNumericPredicateValidation` confirms ordinary fixed uint predicates accept noncanonical spelling. Numeric bindings have a different, strict canonical contract. No algebraic child sorting or simplification should silently rewrite current identities or scope. Adding a parent AND can exceed depth 4/node 32 even when a standalone expression passes; report the combined budget at the relevant span.

Store an authoring envelope with source bytes, source hash, dialect/compiler contract version, library/overload versions, signal/binding schema, normalized predicate and semantic digest. Verify source and IR agree on save/load; avoid independently writable dual authorities. A comment-only edit changes the source hash, not executable identity. Retain current package/definition revision meanings separately: `exploration/package.go:Revision` and `measurements/revision.go` hash validated declarative definitions, not CEL provenance. Compiler upgrades should trigger explicit recheck/migration, never reinterpret old source silently. No prerelease compatibility floor requires preserving a weak pilot wire format; replace it deliberately if necessary.

Retain syntax/source spans separately from the execution IR. CEL checker errors already carry useful positions, but custom lowering errors are currently plain `fmt.Errorf` strings without node ranges. Add stable diagnostic code, stage, CEL expression ID/source range, logical field/binding and relevant budget/capability detail. Preserve incomplete text drafts independently of the last valid IR. An invalid edit cannot become runnable, replace held evidence, or overwrite a saved valid predicate. Apply must atomically validate source, representability, combined parent and backend capability; stale compile responses need a draft revision guard.

P0 acceptance: table-driven bidirectional coverage for all existing predicate variants or explicit supported-subset refusal; generated parse/print/lower identity cases; original comments retained until an intentional visual rewrite; missing/empty/invalid/valid matrix and uint64 edges; backend-independent reference parity; whole-parent OR preserved under AND; invalid/stale drafts cannot apply; precise unsupported-call and expanded-budget spans. Source-free tests suffice for authoring-state admission, but backend semantics require actual adapter parity tests.

## P1 coherent measures and portable extensions

`Query` carries `Numeric`, histogram, summary, status/severity, grouping and time projections (`exploration/model.go`); `TelemetryPackage` repeats these while requiring `Measure == "captured-record-count"` and the ClickHouse adapter (`exploration/package.go`). `workbench/view_declarations.go:Validate` derives available display values from `ViewMeasureFields` and checks numeric binding identity on reuse. A predicate helper is not a measure declaration: severity filtering and `LogSeverity` projection remain different operations.

Before broad authoring, introduce a typed declarative measure/projection sum type or central checked descriptor instead of adding more unrelated flags and CEL builders. Derive package admission, view measure discovery and backend capabilities from that common contract. Keep windows, grouping, measure denominator/unit, presentation and source binding explicit around CEL predicates. Views choose checked measure outputs; they must not execute hidden CEL or manufacture new source scope. Since this is prerelease, refactor duplicated flag plumbing and retire obsolete forms with clear errors rather than indefinitely supporting competing representations.

Extend the ordinary typed IR only when a new operation cannot be expressed faithfully. Severity is a useful example of a helper fully expanding into existing primitives. For nonexpanding operations use versioned semantic opcodes with typed operands, missing/error rules, deterministic reference semantics and static expansion/cost limits. The extension manifest should declare overload IDs, argument/result types, signal/domain restrictions, semantic version/digest, dependencies, required source capabilities and conformance vectors. Registration of a CEL runtime function must never imply authorization to lower or execute it on a backend.

Initially admit reviewed declarative expansions or built-in semantic opcodes. Do not make arbitrary Go callbacks, SQL fragments, network calls or dynamic binaries an end-user package feature. A future runtime isolation mechanism needs its own design. The existing constant-work Go severity function is trusted product code, not a sandbox for third-party code. CEL cost limits do not bound arbitrary host execution (`querycel/library.go` and pilot documentation).

Each backend owns translation from logical fields and typed operations to parameterized source code. ClickHouse's map lookup default requires explicit `mapContains`; nullable/absent Spark/Databricks map values need their own presence and null policy, uint64 range representation and exact decimal overflow checks. A manifest claiming portability is insufficient: require the same boundary/state fixtures against the real target. Existing prepared-fact portability does not establish record-expression portability. Return structured unsupported capability before execution; never fall back to evaluating a loaded page.

P1 acceptance: one extension's versioned conformance suite runs through checked CEL, ordinary reference IR and each claimed backend, including non-ASCII/literal escaping, absence, malformed numeric data and uint64 extremes; unsupported backends refuse at plan time. One query/measure descriptor drives package/view availability and preserves units, denominators and projection identity across authoring.

## Defer

Whole-query CEL builders, arbitrary arithmetic/regex/comprehensions, general negation, dynamic attribute keys, unknown propagation, user-installable host functions and unrestricted extension registries. None is necessary to connect a carefully bounded refinement draft to the app. Databricks record support should remain unclaimed until implemented and verified, rather than blocking a clearly scoped ClickHouse editor.
