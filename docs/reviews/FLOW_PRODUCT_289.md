## Judgment

The planned Activity → focus one signal → author a time-aware view → preserve an
explanation loop is now connected.286 makes single-query authoring reachable from
the ordinary two-signal canvas.287 supplies useful latency measures through the
same timeline.288 makes saving intent, presentation and evidence discoverable
without creating another durable object. These are material capability gains.
The next round should turn this into a faster, easier investigation workflow,
rather than extend the framework or add more chart kinds in isolation.

The immediate implementation candidate is **record paging without unused aggregate
work**, conditional on source measurement. The highest-value subsequent product
capability is **compare this scoped finding with an explicitly chosen baseline**
inside the reusable view. The latter needs a bounded acquisition/interaction
contract first; the earlier reviews' comparison recommendation remains relevant.

## Priority 1: make paging cheaper when measurement establishes the cost

A responder should be able to inspect the next record page without paying for
another aggregate and timeline that the screen does not adopt. Measure statement
count, response bytes and bounded elapsed time with a realistic grouped/time
question; a single extra HTTP request count does not reveal its internal SQL work.
Treat latency as an observation under that fixture, not a production benchmark.

If the work is material, use an explicit records-only acquisition path owned by
the existing fixed query application. Keep the full root query/scope exact and
its page bounds explicit. Preserve the held aggregate and timeline content,
identities, support and clocks; publish only the new bounded record page. Do not
change the measurement total to the page length or imply a transactional snapshot.
Canceled or stale page reads must not replace the owner. Opening a definition and
changing presentation remain source-free.

Acceptance: a real population larger than one page, with aggregate and latency
intervals → next page → new record page and page clock, unchanged held group/time
identities → return or stage an interval → explicit Run refreshes the owner.
Show reduced internal source statements/bytes beside the prior path, check exact
selector/predicates/window, and cover a late arrival without silently refreshing
the held total. Retain existing pending selection, budget and stale-owner guards.
This is an internal implementation change with a direct interaction benefit;
it does not warrant a second user-facing paging mode.

If measurements show negligible unused work, record that result and move directly
to the comparison proposal. Do not spend a milestone inventing optimization hooks.

## Priority 2: a bounded comparison in an authored investigation

Proposed outcome: a responder who finds a latency burst can ask **“How does this
population differ from the baseline I chose?”**, keep the same presentation, and
revisit the explanation without guessing which inputs were reacquired.

Start with one ordinary fixed record-query profile and an **explicit existing
capture reference** for the baseline. That makes baseline custody/read effects
concrete and reuses current stores and operand checks. Do not silently turn a
saved question or view into evidence. Decide compatibility against existing
comparison semantics—signal, selected measure, grouping/bins/units and checked
scope policy—before enabling the action. Report the specific incompatibility;
never coerce a capture into matching by dropping its filter or environment policy.
Do not assume that this proposal already fits an existing comparison card schema.

The suspect side also needs an explicit acquisition policy: either an identified
held result admitted by the existing comparison path or a deliberate new capture.
The UI must say which it uses before reading. A baseline and suspect with matching
windows are still independent observations. Side clocks, support, population
extent and unknown sampling remain separate. Duration comparison uses existing
raw-span measure semantics, never subtraction or averaging of percentile buckets
to construct a new percentile.

A minimal proposal should define one supported representation and comparison
operation, an explicit operand picker, disabled-state reasons, and a save/reopen
story. Use existing aligned components/math when compatible. Side selection should
emit typed intent to the host and stage the correct side's scope; passive children
must not query. Save a definition/reference separately from evidence, as288 teaches.

Acceptance: narrow a real burst → select an existing compatible baseline capture →
see side-by-side aligned values with clear scales and exact support → inspect one
side without losing the other → preserve/reopen with no implicit telemetry read.
Include incompatible baseline, zero/no-support, stale owner and pending-note cases.
Do not introduce arbitrary multi-query children, baseline query scheduling or
multi-aspect capture fusion as prerequisites. Write/review this contract before
implementation; it is the next feature proposal, not a claim of delivered support.

## Supporting simplification, kept proportional to those outcomes

Actual [286 focused records](../journeys/screenshots/286-focused-log-composition.png)
show per-row Inspect, Surrounding logs and missing-trace prose stacked above a
large row height. Preserve the log message as the visual center: keep the primary
inspect gesture immediate and consider compact secondary actions and a brief
unavailable trace indicator. Preserve accessible names and keyboard access. The
fixture's sparse content is not evidence about all production row layouts.

The [288 expanded Preserve](../journeys/screenshots/288-explicit-signal.png) clearly
separates its meanings and correctly requires a signal. Its Finding textarea and
attachment explanation consume substantial space even when the immediate goal is
Save view. Put that attachment form behind a contextual **Add to investigation**
disclosure after a current saved ID is available; retain the direct Save and exact
revision guards. This is a small supporting adjustment, not the sole next outcome.

The [287 latency timeline](../journeys/screenshots/287-duration-timeline.png) is
visually useful: the burst, zero and empty intervals are distinguishable. Evidence
chips and repeated “approximate geometry”/capture prose can eventually be grouped
into one concise status plus exact disclosure. Do not remove unavailable/unknown
semantics or hide source/read distinctions merely to shorten the screen.

The [288 investigation](../journeys/screenshots/288-preserved-pieces.png) honestly
shows three objects, but also repeats definition/capture explanation and long IDs.
Prefer concise object badges and read-effect summaries with exact details behind
disclosure as future cards are touched. An empty “No captured evidence linked”
panel should remain a clear state without becoming a large competing card. Keep
raw identity accessible; visual compactness must not weaken immutable references.

These observations should inform the next real workflow, rather than trigger
another isolated whole-UI rewrite or a cosmetic component migration.

## Roadmap disposition and lessons

- Mark the focus/timeline/preserve sequence complete. Supersede old “next” labels
  through a dated checkpoint; retain historical reviews as history.
- Measure paging first and optimize only the demonstrated unused work. Then design
  the bounded baseline comparison. Do not multiply service templates or chart
  types to avoid the harder connected investigation outcome.
- Keep the whole-UI grammar as the direction, with explicit bounded source/input
  profiles. Arbitrary grids, full WYSIWYG, marketplaces, new chart engines and
  universal saved objects remain unjustified for this next cut.
- Preserve separate production workstreams for authentication/source isolation,
  retention/quotas and durable alert delivery; the completed investigation loop is
  not evidence of operational readiness there.
- 288's bugs arose at integration boundaries: moved editor ancestry, held-parent
  owner lifetime and invocation-time publication guards. Test actual Apply,
  Back and stale-action paths in each new journey. Source ownership is not the
  same lifetime as a visible configuration command.
- Keep compact observed request/source ledgers, model traces, current frames and
  failure diagnostics. Do not retain bulky successful artifacts without a future
  development use. Assertions should observe outcomes independently; a clicked
  button or conforming unfinished prefix is not completion.
