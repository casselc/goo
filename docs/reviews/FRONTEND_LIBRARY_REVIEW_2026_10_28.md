# Frontend library review — 2026-10-28

**Proposal only; source reviewed at `af107b7`.** No implementation, dependencies, runtime campaigns, commits or performance benchmarks were performed. This review covers the browser library and application broadly, including Python delivery and Go/API seams. Source line references identify the reviewed snapshot; many JavaScript lines contain whole functions.

This is a prerelease project: current browser requirements, classic-script/CommonJS entrypoints and element APIs are facts to evaluate, not fixed compatibility floors. Breaking those interfaces is negotiable when it produces a concrete benefit. Evidence history and development artifacts are also negotiable: obsolete prerelease formats may be retired or reseeded deliberately. Keep exact telemetry semantics and useful capture/reuse behavior where they support actual workflows; do not preserve every receipt, ledger or old fixture as an end in itself.

Goo already has the right foundation: framework-neutral supplied-data elements, typed presentation adapters, explicit application request owners and native semantic HTML. The useful next library work is to make those boundaries easier to maintain and verify. A new framework, universal query component or public subscription API would add obligations without a demonstrated benefit.

## Prioritized recommendations

### 1. P1 — Give request cancellation an explicit response-consumption contract

`GooQueries.post` returns a raw Response and removes its abort listener in `finally` (`ui/queries.js:7–8`). Fetch resolves at headers, whereas owners subsequently await JSON (`ui/host-counter-pair.js:22`, `ui/live-comparison.js:75`). Browser abort still affects the body, but the separate server cancellation POST no longer runs after headers. This is an identifiable lifecycle boundary, **not evidence of a demonstrated backend leak**.

First document and test when Go execution/admission is released, including Python forwarding. If cancellation must cover body consumption, add an internal typed JSON-read helper that keeps registration through decode; decide raw Response retention from actual consumers, and keep SSE separate. Before: `response = await GooQueries.post(...); data = await response.json()`. Possible internal after: `data = await queryJSON({url, body, signal})`, with explicit status/error handling. No change to routes, public element inputs or query IDs is proposed.

Benefit: a single comprehensible cancellation/error boundary. Tradeoff: callers currently inspect different errors and statuses; migrate two actual owners first and preserve their messages. Validate abort before headers, delayed body, malformed JSON, non-2xx, obsolete completion, server admission release and absence of extra retry/read. Coordinate the normative lifecycle and fixtures with the Go review.

### 2. P1 — Separate owner utilities from feature modules, then adopt narrowly

`RequestOwner` already exists in `resource-scope.js:5`; `PendingScope` already exists in `numeric-distribution-comparison.js:3–8` and is reused by unrelated features. Their homes obscure their general mechanical purpose. `live-comparison.js:85` separately observes the entire document body for removal. Move proven generic utilities into a small internal owner module while retaining distinct contracts: generation/cancel, event cleanup, owner removal and domain publication eligibility.

Before: unrelated modules reach into `GooNumericDistributionComparison.PendingScope`. After, internally: `GooRequestScope.PendingScope`, with a direct coordinated rename of in-repository callers; add a temporary alias only if an identified external consumer needs a migration window. Preserve host visibility, open-panel, selected-identity and active-route predicates (`host-counter-pair.js:15–16`); a generation alone is insufficient. Require explicit dispose from composition roots where available; retain removal detection as a fallback until callers reliably dispose.

Benefit: clearer dependency direction and easier cleanup verification. Fewer observers might reduce work, but no CPU/memory improvement is measured. Avoid a global observer bus or generic effect runtime. Validate delayed completion after close/switch/dispose, listener removal, repeated mount/unmount and parent restoration, using the existing history owner campaign as a model.

### 3. P1 — Make browser/server semantic mirrors a fixture-backed contract

`question-session.js:4–6` normalizes record identities; `host-counter-pair.js:8–10` independently canonicalizes exact native questions and validates basis/window/stream results. These serve different domains. Do not replace them with one generic stable stringify. Likewise, browser geometry and native result projections are useful local computations, not reasons to call a server for every display update.

Create a small contract inventory identifying each normative Go type/function, browser adapter and complete shared fixture. Extend the existing wire-fixture approach with missing versus present empty, absent optional defaults, large integers, exact nanosecond bounds, negative instants, unsupported fields, wrong stream/schema, temporality and unknown intervals. Keep query authorization/validation server-authoritative and any IDs still used by supported capture/reuse workflows correct; old prerelease artifact formats may instead be explicitly retired.

Benefit: safe extraction and independently usable presentation. Tradeoff: fixture maintenance; avoid a second handwritten schema system. Migrate one native paired-result validator and one record identity adapter first; require expected rejections as well as accepted fixtures. Any generated schema must preserve decimal strings and optional-field meaning.

### 4. P2 — Extract private element mechanics without changing element semantics

Property upgrading, bounded JSON parsing and reactive rendering repeat across `components.js:24–59`, `evidence-summary.js:11–15` and chart modules. However, they intentionally differ: chart frame preserves child nodes; evidence summary preserves its disclosure and focused summary; snapshot elements may replace content. Attribute budgets also differ (core 64 KiB, evidence summary 512 KiB).

Inventory those differences, then share only private leaf helpers such as property replay and caller-parameterized JSON parsing. Keep per-element validation, snapshot-copy policy, state mapping and rendering explicit. Avoid a public base class or universal renderer. Before/after user code stays `element.data = suppliedFacts` or server JSON attributes; no lifecycle fetch or navigation is added.

Benefit: fewer upgrade/parser mistakes while preserving SSR reuse. Tradeoff: another dependency must load before definitions; choose and document the supported standalone entrypoint before adoption; classic-script compatibility is negotiable. Pilot with two compatible snapshot elements, not child-preserving chart frame. Check pre-definition detached assignment, attribute/property precedence, malformed/oversize JSON, reconnect, input mutation isolation and zero API requests.

### 5. P2 — Consolidate composition styling after confirming actual ownership

`product.css` contains successive `.dashboard-grid` rules at 1041/1129/1135, `!important` application reductions at 1160, and population composition rules from 1166 onward. This indicates layered evolution, not by itself a visual defect. Feature styles already exist and should remain separate from reusable element styles.

Move only stable owner rules into the existing feature CSS when touching that composition. Tighten selectors to owning children; delete superseded rules after computed-style/visual parity. Reuse the implemented `mountFacets` rather than hiding another full workspace with CSS. Do not introduce Shadow DOM, container-query variants or cascade layers across the entire product as a prerequisite.

Benefit: predictable standalone/nested sizing and less accidental cross-owner influence. Tradeoff: ordering changes can expose previously masked dependencies. Validate keyboard table scrolling, mobile overflow and sticky overlap, nested inspector layouts, authored children and host family switching. Refresh affected storyboard frames from the running app when implementation occurs.

### 6. P2 — Inventory delivery dependencies before optimizing startup

`index.html:38–50` eagerly loads the feature catalog as ordered classic scripts; `server.py:126–132` separately allowlists assets. `components.html` has its own display-only dependency set. The risk is dependency drift and unnecessary startup work; current source alone does not quantify the user cost.

First create a machine-readable internal asset/dependency inventory and a check that both entrypoints load their declared dependencies, static delivery is allowlisted and the gallery needs no query client. Keep the existing explicit serving policy; do not replace it with arbitrary filesystem serving. Measure transferred bytes, parse/evaluation time, requests and first usable Explore interaction under a documented cold/warm profile. Only if material, introduce one optional feature loader or build-time bundle with the agreed embedding APIs and fallback behavior explicitly documented.

Benefit: reliable composition today, evidence for optimization later. Tradeoff: manifest generation can become a build burden; a validation-only inventory may suffice. A direct ESM cutover is the preferred maintenance proposal below; bundling remains a separate measurement-driven decision. No dependency installation is performed by this review. Preserve Python lab startup and source-free navigation.

### 7. P2 — Finish adoption through supplied facts, not a universal result API

`evidence-scope.js` already transforms native, record and service-widget facts; `definition-library.js` already handles typed revisions and local catalog bounds. Complete adoption where a real duplicate remains, using these APIs rather than adding new evidence/catalog elements. `record-results.js:5` still constructs qualified field labels locally while `field-presentation.js` already provides family-aware labels. Inventory residual label/table/comparison duplication before extraction.

Share a small application composition only after two compatible consumers prove it. Keep stored comparison, explicitly fresh reread and rolling baseline ownership distinct; independent clocks and incompatibility notices remain visible. Unsupported numeric domains retain exact table fallbacks. Benefit is consistent compactness and clearer actions; tradeoff is preserving meaningful family differences rather than maximizing reuse. Validate missing/empty fields, duplicate-title revisions, selected detail outside a filtered page, known-to-unknown transitions, exact scope and explicit Run behavior.

### 8. P2 — Make conformance coverage discoverable and accessibility explicit

The repository already tests important invariants: component journeys assert no API reads; `chart-frame-components.spec.js:5–21` checks SSR, detached updates and preserved caller focus; component tests check table keyboard scroll; history ownership tests delay real responses. Preserve this layered evidence rather than running every campaign for every extraction.

Maintain a compact contract-to-test matrix next to UI_COMPONENTS: input/update/reconnect, child identity, selection intent, exact fallback, keyboard/focus, no effects and nested/mobile composition. Add only missing contract tests during adoption. Include heading outline, visible focus, result-state announcements without repeated chatter, disclosure return focus, brush keyboard alternatives and exact timestamp access beyond mouse hover. `evidence-summary.js:15` exposes exact times via title and focusable time nodes; inspect assistive-technology discoverability before claiming equivalence to visible exact text.

Use pure Node tests for validation/geometry, standalone browser conformance for DOM semantics, representative real OTel journeys for wire/adoption, and Bombadil/observed traces for races and hidden effects. Existing storyboards remain product evidence, not synthetic gallery substitutes. No new suite was run for this document.

## Preferred prerelease modernization and cutover proposal

**Prefer a coordinated native ESM cutover for browser display and application modules**, subject to design/usability confirmation of the changed embedding instructions. The source-backed benefit is dependency ownership: today `index.html:38–50` manually orders a large script catalog, feature modules resolve globals or CommonJS, and Python maintains another asset inventory. Explicit imports make dependencies locally reviewable and allow Node/browser tests to import the same implementation without dual export branches. This is a maintenance/reliability proposal; no startup speedup is claimed. ESM itself does not eliminate the Python allowlist or guarantee fewer requests.

Proposed external integration changes from `<script src="/components.js"></script>` to `<script type="module" src="/display.js"></script>` for the core display entrypoint, or a documented direct feature-module import. Existing supplied JSON attributes, detached properties and selection intents remain initially unchanged because their semantics already fit. Classic globals/CommonJS exports can be removed in one prerelease release once the consumer inventory confirms in-repository examples/tests are the consumers. Do not require aliases simply to preserve an implementation that is being deliberately replaced. If real external consumers exist, agree a migration window explicitly rather than assuming either indefinite compatibility or zero migration cost.

Start with the display graph, then the application graph. Establish a tiny shared display utility module with explicit imports; use separate display and application entrypoints so importing a chart cannot bootstrap queries/navigation. Update standalone server HTML, SPA examples, Node test imports, asset registration and documentation together. Test module execution's deferred timing, pre-definition property replay, circular dependencies, duplicate element registration, failed imports and reconnect. The standalone gallery must still make zero API requests; the first app cut must preserve explicit Run and cancel/dispose ownership. Keep the old graph only until the chosen pilot passes, then remove it rather than maintain two permanent runtime systems. Costs include widespread import edits, example/test migration, module MIME/URL handling and potential cycle discovery; split pilots into reviewable cuts rather than mix this with CSS or telemetry changes.

Adopt a documented evergreen-browser policy as part of that decision. A reasonable proposed target is current and previous stable Chromium, Firefox and Safari, with exact tested versions recorded at implementation time; this is a proposed support target, not established evidence. Run the small display conformance set across all three engines before claiming it. Choose a narrower target explicitly if project priorities warrant it. Newer APIs may raise this negotiated baseline when they remove enough code or improve a demonstrated interaction; fallback code is justified only for browsers the project actually supports. No browser download or new campaign is performed here.

Keep bundling optional initially: native ESM gives the dependency benefit without a new build requirement. Compare cold/warm transferred bytes, request graph, parse/evaluation and first useful interaction before adding an optimized build. A build that materially improves those measurements can replace source delivery, provided standalone display imports remain straightforward and source maps/debugging are usable. Similarly, breaking a public element API is available if two real consumers demonstrate a simpler supplied-data contract, but no specific element-shape break is justified by this review. Evaluate captured JSON, IDs, custody clocks and retained formats as separate product/data decisions too: preserve only required reuse, debugging or future-feature value, and explicitly obsolete/reseed disposable prerelease artifacts when that is cheaper.

This proposal supersedes any earlier wording that treats current script formats, API names or browser support as immutable. The earlier recommendations' semantic guardrails remain: passive displays, framework neutrality, SSR/SPA usability, exact/unknown states and app-owned effects. Root should obtain API/usability confirmation of the ESM embedding change before implementation; this document authorizes no code, dependency or framework migration.

## Retain and reject

Retain light DOM/native tables and disclosures; bounded supplied snapshots; pre-definition property upgrade and SSR fallback; standard OTel resource/schema/temporality interpretation; app-owned navigation, cancellation, source reads and publication; exact/unknown states; explicit fixed scales/rescale in live comparisons; source-free reopen and parent return. Keep the compact consolidated host controls and Evidence region rather than reintroducing per-widget workflow chrome.

Reject a framework migration, public subscribing dashboard element, universal query/result blob, global mutable UI store, automatic mount/disclosure reads, generic numeric coercion, virtualized datagrid without measured need, automatic semantic compatibility inference and a package publishing effort before an external consumer exists. Native SSE comparison delivery may be useful later, but should replace a measured polling/reliability limitation through an app-owned protocol; it does not belong in element lifecycle. Public advanced APIs require a concrete performance, reliability or usability benefit and design/usability confirmation. The proposed ESM embedding break requires that confirmation; it adds no query or display concepts.

1. Record current contracts and dependency/fixture coverage. Use `af107b7` host behavior and examples as the comparison baseline; decide which contracts remain useful rather than freeze them all.
2. Resolve response-consumption/cancellation semantics with Go/Python owners; pilot the internal helper in two owners.
3. Relocate existing owner mechanics and migrate representative consumers, deleting duplicate cleanup only after race parity.
4. Extract private input/lifecycle leaves with standalone SSR/SPA tests; preserve intentional per-element differences.

Each step should remove its superseded path, negotiate migration only for identified consumers, and state actual checks and remaining limitations. Success means fewer places to encode a contract, intentional request behavior and understandable compact UI—not merely fewer files or a more elaborate public API.
