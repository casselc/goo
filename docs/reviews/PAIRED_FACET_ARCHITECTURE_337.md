## Authority and data boundaries

A fresh fixed-query count comparison already owns two checked questions: the
selected root and the comparison's baseline recipe. Each keeps its exact window,
typed environment policy and complete original predicate. Neither a loaded record
page nor the facet's value list replaces either operand. Values/counts in this
first cut describe **Selected window values** under its applied scope, including
existing filters on the facet itself; they do not imply baseline absence.

Permit the existing categorical facet with only the fixed-query comparison arm.
Validate the declaration against both questions. Captured baseline and temporary
selected/rest comparisons retain their existing custody/set contracts and remain
outside this feature. The five unique roles may coexist (aggregate, records,
timeline, comparison, facet); five is still a fixed closed bound, not recursive
layout. Duplicate roles or an additional child refuse.

The pure browser planner accepts one to 32 closed categorical intent items with
exact signal and qualified field matching the current facet. It reuses the
existing selection builder, retaining include-OR, missing-aware exclusions and
missing versus present-empty semantics. It clones both operands, validates both
complete candidates and the resulting composition before returning either.
Failure on only the baseline's predicate budget must leave both original
questions and the authored declaration unchanged. Arbitrary origin/source fields
cannot cross this pure intent boundary.

## Ownership and continuation

The application stages common narrowing via the existing child/task owner.
**Filter both windows** has zero source effects; explicit Run uses the current
pair acquisition owner. While a new task is staged, the supplied parent pair
remains immutable. Existing generation, draft, live-context and membership checks
must retire stale counted-value gestures and late responses. No universal route
manager or new cache is required; 335 saved-visit handling remains authoritative.

A group-side supporting-record child is a distinct single-operand task. Because
facet and comparison now coexist, the old default facet inheritance must not copy
the whole parent comparison into this records-only child. Preserve the checked
facet with an explicit records-only composition, or deliberately omit it; keep the
chosen operand's exact question and one independent record read. Copying the
parent pair here would silently add a different comparison and extra source read.

Save/export/reopen preserve the checked facet and both questions, never loaded
values, pending choices or observations. Reusable template rules are independent:
this change does not make arbitrary fixed-query comparisons category templates.
