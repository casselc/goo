# Product next cut after Go maintenance — 336

Status: proposal from source/document review, not delivered functionality or a new
browser audit. Product and design reviewers independently selected the same gap.

## Judgment

After the 336 dependency update, ship **337: narrow a fresh comparison with an
existing categorical facet**. Follow with **338: compare the facet's category
populations across both windows**. This returns the cadence to general-purpose
scope composition, then depth, rather than extending route ownership work.

The product remains Activity → isolate scope → inspect/compare → preserve/reuse.
The useful addition is a natural narrowing control that survives comparison,
not another dashboard entrance, renderer family or saved-object type.

## What already works, and what is missing

- Activity stages a fresh previous-window count pair (333); its windows, typed
  environment and original predicates survive. Explicit Run reads both full
  populations; group actions stage exact supporting-record questions (334).
- Contributed categorical facets already read full applied-scope values explicitly,
  stage Include/Exclude choices, and reuse the population's Apply/Open workflow
  (310/311). Missing and present-empty values remain distinct. Their declaration
  survives Save/export/reopen and team templates.
- These features do not compose today. `ui/view-composition.mjs` explicitly rejects
  facet plus comparison; `workbench/view_composition.go` enforces the same boundary.
  Population authoring requires removing the facet before adding comparison.
  Manual query filtering exists; the gap is retaining a reusable field control
  with an explicit common effect over the pair, not a lack of a predicate engine.
- The 335 visit owner now protects staged definitions and held local tasks. Reuse
  it; scope composition does not require another router, cache or execution owner.

## 337 — common categorical narrowing for fresh fixed pairs

Journey: a responder sees a service change in Activity, stages the existing
previous-window comparison, and chooses its contributed HTTP method or route
facet. Read values explicitly, choose POST, review **Filter both windows**, then
Run. Both questions retain their own fixed interval, policy and original filters;
the additional condition applies to each. Inspect a changed group's records,
return to the pair, then Save/export/reopen the same reusable intent.

Bound the first cut to ordinary logs/spans **fresh fixed-query count pairs** with
an eligible categorical field on both questions. Existing fixed-baseline names
and Previous/Selected window names must remain accurate. Frozen captures and
held selected/rest/overlapping-parent comparisons keep their existing contracts;
this proposal does not redefine their custody or set relationships.

Required acceptance:

1. Keep the existing facet declaration and passive element beside Summary/Groups;
   no second facet kind or bespoke comparison filter language. The control's
   applied values/counts are explicitly **Selected window values** in this cut.
2. Stage the same qualified Include/Exclude delta onto both original predicate
   trees. Preserve each complete AST, exact interval, typed environment and
   category/grouping intent. Validate both candidates before committing either;
   a budget/compatibility refusal must leave both unchanged. Different original
   predicates remain different; common narrowing does not claim identical scopes.
3. Opening, editing, selecting and clearing pending choices perform no telemetry
   read. Run uses existing pair acquisition. Values retain the applied-scope
   denominator, including their own field's existing filters; do not quietly
   introduce self-excluding facets or treat loaded rows as totals.
4. Keep applied pair facts immutable while a new scope is staged; retire stale
   counted-value gestures and source adoption on scope replacement. Save/YAML
   retain both checked questions and the facet, never observations or pending
   selections. Removing a facet control does not remove applied filters.
5. Verify logs and OTel spans (for example `http.request.method`), literal versus
   resource fields, missing/empty values, predicate budget refusal and distinct
   current/effective environment policy. Use actual Go/JS/YAML admission properties,
   a native OTLP storyboard, and a positive-completion Bombadil journey. Native
   inspection must show the plotted pair and relevant facet without a settings wall.

Reuse `facet-declaration`, `categorical-facet`, counted-values/source snapshots,
existing selection tray and paired query/window validation, `view-composition`,
`captured-count-comparison`, and the shared passive pair presentation. Extend
existing application adapters; display elements still do not fetch or navigate.
No legacy format accommodation is necessary, but the new semantics must be typed
and explicit in Go, the browser grammar and portable YAML.

## 338 — explain category shifts across both windows

Extend the same control with an explicit read of both operands' full-scope category
values. Show a shared-scale union with each window's count and exact change;
a baseline-only category must remain visible and selectable for common narrowing.
Use separate checked read clocks/coverage for the two witnesses and the existing
passive comparison contracts. Unequal windows remain raw counts, not rates.

This is new data depth, not formatting the selected list as a fake comparison:
loaded record buffers, a selected-side lookup or a missing value in a limited
response cannot prove the other side is zero. Unknown/incomplete/change-between-
reads states must remain visible and refuse unsupported actions. Preserve the
337 atomic scope and explicit-read contracts. Do not bundle statistical anomaly
claims, arbitrary transforms, multiple-facet layouts or frozen-custody semantics.

A checkpoint after these two cuts should select the next breadth task from real
usage and measured gaps. Do not expand them into a dashboard-parity catalogue or
return to speculative state-manager rewrites.
