# Team template from service evidence — design review 356

Status: source and three actual frames accepted. Subsequent canonical execution
passes; see [validation](../../VALIDATION.md). The contract and review stages below
cover ordinary record/aggregate reuse through the existing saved-view catalogue.

A user has a useful scoped service widget and wants the team's reusable view of
that population. The interface should connect the existing Customize handoff to
existing saved-template inspection/application. It must not send the user to a
new workspace or bury the telemetry under a new authoring wall.

## Existing capability and entry

Service widgets already prepare checked view configuration through Customize and
stage it in the population workspace with a return path. Population saved views
already expose Inspect template, checked metadata expansion, compatibility preview
and local Apply template. Their saved question is a validation specimen; it is not
a source population to borrow.

Use one contextual action such as **Use saved template** beside the existing widget
Customize flow, optionally inside Widget actions when primary space is limited.
It opens the same destination population and deliberately reveals/focuses the
existing saved-template choice. No automatic loading of every template on service
entry, second catalog/store, sidebar or new view runtime is needed.

Keep Open original question clearly distinct from Inspect/Apply against the current
scope. Opening the specimen is an intentional different question; it must not be
the hidden implementation of applying a team template.

## Preview, Apply and Run

Inspect fetches configuration and performs pure expansion/compatibility checking.
It reads no telemetry. The existing preview should state the destination qualified
grouping/profile and show concise applicability; full question/policy facts stay
inspectable through existing disclosure. Avoid another repeated paragraph of
scope above the already held data.

Apply template changes presentation locally and keeps the whole destination query,
typed environment policy, service/namespace predicates, fixed UTC window and held
observation receipts. The category binds only to the destination's admitted grouping;
no automatic grouping or profile filter is invented. Literal record columns/facet
fields retain their declared semantics. A template's specimen service/environment/
clock never substitutes for current investigation scope.

Existing explicit Run acquires fresh data under that fixed configuration. Apply
and Run must remain visibly distinct actions with truthful no-read/read status.
If the current destination is ineligible, show the specific compatibility reason
beside disabled Apply. Unsupported numeric/native/comparison/timeline variants
remain outside this first bridge unless already admitted by its closed contract.
Do not expand applicability merely to make a demonstration succeed.

## Return and ownership

Back restores the original service widget and its independently observed evidence,
without rereading successful overview cards. Restore focus to a current visible
semantic opener and preserve relevant local template choice/preview while the
population owns the visit. Dirty population drafts keep their existing acceptance
rules; a template action cannot silently discard them.

Service/profile/range changes, departure and newer catalog inspection retire old
metadata/expansion work. A late response cannot apply to a newer destination even
if the title or service text matches. Detached Apply/Open handlers stay inert.
Catalog selection/search is configuration state, not source capability or proof
that the team template targets this particular service.

## Acceptance

Use a genuine OTel service widget and a saved ordinary template whose specimen has
a different service/window. Open the contextual choice, inspect compatibility,
locally Apply, explicitly Run, inspect supporting records and Back to the original
service. Verify exact destination policy/predicates/grouping/bounds, retained parent
receipts and zero telemetry reads for catalog/inspection/Apply/Back. Save/reopen
uses the existing authored declaration and does not borrow the specimen data.

Include wrong profile/missing grouping, dirty destination, wrong expansion echo,
late service change and old-handler negatives. Actual desktop/narrow frames should
show a compact contextual entry, readable compatibility, destination data and
current return focus. Task-scrolled catalog screenshots do not prove whole-entry
above-fold density; record actual entry positions if making that claim.

## Frozen source acceptance

The implementation adds Use saved template as a secondary widget action only for
supported completed ordinary page-zero grouped record questions. It waits for
all overview pending work before allowing the handoff, preserving the existing
held service return contract. Unsupported specialized/native questions do not
receive an apparently usable action.

The exact detached destination question passes through service browser, trail and
Explore into the existing population stage path, with recent mode disabled and an
intent flag that deliberately reveals/focuses the current saved-view library.
Catalog acquisition remains metadata; Inspect/checked expansion, local Apply and
explicit Run retain their existing roles. The specimen query and a default grouping
are not substituted into the current destination. Source review accepts the bounded
bridge without a new workspace/store. The initial child stages configuration and
has no borrowed source page; the original service evidence remains held separately.
Actual contextual preview, staged and applied frames are reviewed below.

## First actual-frame acceptance

Reviewed `356-compatibility.png`, `356-staged-390.png` and
`356-applied-template.png` at original detail. The existing catalog clearly
separates Open original question from Inspect template. The selected preview
identifies destination `column:name`, current effective policy/fixed bounds and

Narrow staging retains Back to service, configured scope, explicit Run and a

operation names, exact support counts and an existing List record presentation

These three current frames pass visual acceptance. Their task positions do not
establish fresh service-entry above-fold density. Exact no-read planning/Apply,
question/policy preservation, save/reopen and Back ownership remain native-ledger
assertions rather than screenshot inferences. Execution gates are still pending.

The now-reachable existing catalog repeats template titles in row text and Inspect
buttons and appears beneath authoring controls. That is a concrete presentation
opportunity for the already selected 358 consolidation, not a 356 blocker or a
new parallel layout queue. Preserve readable destination facts and zero-source
compatibility while reducing redundant labels/authoring prominence there.
