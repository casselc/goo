## Recommended breadth → depth → consolidation

### 1. Breadth: usable typed-scope service continuations

**Journey:** discover services under an effective/empty/unreported policy, view
reported relationships, open the wider child service population or reuse a saved
Activity view, then return without changing policy or reading implicitly.

Source gaps are concrete. `ui/distributed-services.mjs` builds both wider and exact
edge questions with only `environment: scope.environment`. Typed discovery already
uses the shared checked predicate (`service_discovery.go`), but these links lose
that selector. `mount` immediately constructs exact-edge step links; an unsupported
question can throw during rendering before the wider link is usable.

Separate capabilities deliberately. The first cut should carry shared typed fields
into the already-supported wider child question and keep exact namespace/window.
For unsupported exact typed edges, show an explicit reason before constructing
that link; do not weaken effective policy to scalar current-only or break the
whole distributed view. Preserve the already-supported scalar path.

The same service browser gates saved Activity views on `currentName`, although
`ActivityViews.library` already accepts a typed scope object through `scopeFields`
and validates returned view policy. Reuse that supported metadata path. This does
not justify unblocking scalar entity-bound deployments/annotations, whose meaning
is different. Saved-view listing is scoped to environment policy, not proof of the
selected service or fixed discovery window: preserve each saved selector without
injecting the current service, and keep its rolling/live configuration explicit.
No new saved-view catalogue or global capability manager is needed.

Acceptance: genuine typed discovery with reported edges, missing/empty namespaces,
current/legacy conflicts and wider child membership; graph renders even when exact
edge capability refuses; saved view listing/staging retains the same policy and
Start stays explicit. Verify zero source reads for display/local return and no
foreign-policy adoption. This breadth task must be useful without pretending the
next exact-edge compiler cut is already delivered.

### 2. Depth: exact typed reported-edge investigation

**Journey:** choose one observed parent→child relationship and inspect only its
reported child-span population within the discovery policy/window.

This requires more than fixing link fields. `Query.Validate` currently refuses
`EnvironmentSelector` with `ReportedEdge`. `compiler.reportedEdge` hardcodes
current-key environment membership in the parent-owner subquery. Typed discovery
already resolves parent ownership under its checked environment; the continuation
must match that semantics before child filtering.

Extend the existing bounded reported-parent path with shared selection predicates
for both parent ownership and child membership. Preserve trace/span identity,
qualified namespaces, ambiguous/unresolved diagnostics and original fixed bounds.
Do not resolve parents after narrowing child predicates, merge conflicting parent
owners, infer async links or rename child-span counts as unique calls/latency.

Acceptance: scalar/typed current-only equivalence and effective named/empty/
unreported partitions; conflicting current/legacy values on both parent and child;
namespace collisions and ambiguous duplicate parent IDs; exact original discovery
predicate before ownership resolution; parameterized source plans and independent
record-membership oracle. Genuine edge→child records→capture/reopen→Back must
retain policy and clocks. Reuse the current source/compiler, not a graph engine.

### 3. Consolidation: independent service-widget recovery

**Journey:** an overview has useful traffic/native observations but one widget
fails. Retry only that widget's same fixed question, retaining successful siblings.

`ui/service-dashboard.mjs` already executes bounded widgets with two workers and
keeps per-widget results. Its worker still turns failures into `Error(data.error)`
and `results` error strings; its error card has no targeted Retry. Reapplying the
overview rebuilds/rereads the successful widgets too. Reuse the 344 refusal parser/
passive renderer and add an explicit current-widget recovery boundary inside this
existing owner, rather than another executor or generic retry service.

Acceptance: fail one real record-aggregate widget and one supported native read;
healthy siblings' DOM/result identities and source clocks remain unchanged, Retry
acquires exactly the failed frozen question, overall status updates truthfully,
and failed/stale data never becomes zero. Profile/window/selection changes retire
pending and saved old Retry handlers; metadata-only edits and Back do not read.
Do not broaden typed native families or reinterpret unsupported prerequisites as
retryable failed reads. Current per-stream unit/temporality/raw identity remains.

## Other material opportunities, outside that finite sequence

- **Current RPC convention profile:** `dashboard.go` explicitly requires legacy
  `rpc.system`/`rpc.method`; `rpc.system.name` already has presentation metadata but
  is not substituted. A separate checked current-convention profile can improve
  ordinary SDK coverage. Verify the applicable current convention/schema first;
  do not alias-union old/new attributes or change measured population by guesswork.
- **Cross-layer request-byte admission:** 343's genuine 512-byte-label comparison
  exceeded the pure 1 MiB body cap despite valid group cardinality. Package limits,
  facet response budgets and comparison-body budgets are distinct. Keep a separate
  bounded admission/feedback proposal; never raise limits globally or claim the
  source-refusal UI/atomic publication solved it.
