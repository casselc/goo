# Whole-product design checkpoint — 351

Proposal only, after the finite 348 breadth → 349 depth → 350 consolidation
sequence. No production, roadmap or browser changes are made by this review.
350's final execution gates retain their own owners.

## Product judgment

The core story is now materially better: watch current ordinary OTel, scope a
population, compare it, explain its composition, inspect exact supporting records,
and preserve/reuse definitions or observed evidence. Fresh-pair explanation closes
a genuine analytical entry gap. Service-local inventory makes a small service
usable inside a large environment. Typed package authoring and Stage → explicit
Run make the grammar available to mainstream scopes without surprise reads.

Latest 350 frames show clear effective-policy labels, fixed versus freshly planned
windows and real duration/status profiles. The initial static “staged” package note
incorrectly persisted after Applied; the regenerated narrow frame's neutral title/
short-revision binding fixes that contradiction. This is accepted bounded polish,
not a reason to keep iterating on package prose or facets.

Automatic service overviews already exist for generic spans/logs, incoming HTTP,
legacy RPC, database clients and messaging role spans, plus bounded exact native
instruments and declared bindings. Record/aggregate compositions, reusable kinds,
templates and portable view artifacts also exist. Do not propose their foundations
again, or claim the larger Kubernetes/USE/broker/WYSIWYG catalogue already executes.

## 1. Breadth: follow distributed services under the policy actually selected

**Task:** from a typed effective/current/empty/unreported discovery view, follow a
reported service edge or inspect its wider child population and return.

`ui/distributed-services.mjs` builds both continuation questions with scalar
`environment: scope.environment`, dropping typed policy. Architecture confirms the
shared Query currently refuses typed selector plus ReportedEdge, so exact-edge
support requires a real compiler/source/admission contract, not only changing the
browser presenter. Discovery itself already accepts the typed scope.

Close that specific gap using existing distributed discovery and query execution.
Preserve complete policy, parent/child namespace/service identities, fixed bounds,
reported-parent interpretation and edge diagnostics. Keep exact edge versus wider
child population visibly distinct; neither is a causal or complete-trace claim.
Stage first, explicit Run, then Back to held discovery with its receipts and focus.
No service-map redesign, graph store or inferred topology is needed.

Acceptance: genuine current/legacy conflicts and empty/unreported environments,
qualified namespace edges, a wider-child contrast, scope-proof negatives and native
return/source counts. This is the strongest next breadth task because current
users can discover data but cannot reliably follow its natural distributed path.

## 2. Depth: update one automatic OTel family with an explicit population contract

**Task:** a service using current RPC conventions should receive an applicable
incoming-work view without disguising it as a legacy profile.

`docs/SERVICE_DASHBOARDS.md` and the existing profile describe an intentionally
legacy RPC lens using reported Server kind, `rpc.system` and `rpc.method`; current
RPC is explicitly deferred. Preserve that honesty. Research the latest applicable
OTel convention first, then implement one named current-convention profile using
its exact keys, presence rules and supported native instrument units. Do not union
old/new aliases or equate span Error with protocol outcomes without a contract.

Reuse automatic candidate selection, explicit profile Apply, existing charts and
supporting-record drilldowns. A missing bounded-page hint is unknown, and an empty
current profile must not silently broaden to All spans. Current and legacy records
should be distinguishable in fixtures and exact queried populations. This adds
useful default coverage beyond the sample without another dashboard framework.
Broader Kubernetes, broker and USE families remain separate entity/source projects.

## 3. Consolidate: make service-local reuse work with typed scopes

**Task:** after inspecting a service, find a saved rolling Activity view in the
same checked environment policy and deliberately stage/start it.

`ui/activity-views.mjs` already accepts typed scope objects for its library, but
`ui/service-browser.mjs` only mounts it when `currentName` returns a scalar; other
policies show Saved Activity views unavailable. Reuse the existing typed library
instead of keeping this stale native-capability gate around a configuration-only
feature. The library remains environment-policy-scoped; matching a service visit
does not prove saved predicates target that service. Opening a definition must not
silently inject the selected service or replace its saved selector. Keep entity/operation/native scalar restrictions where their contracts
actually require them; do not remove all guards indiscriminately.

Acceptance: named effective, empty and unreported service visits show matching
saved configuration, library metadata reads remain distinct from telemetry, and
opening stages before explicit Start. Dirty destination scope and late catalog
responses retain current ownership. This small structural parity cut should also
remove the obsolete unavailable copy and update the corresponding known limit.
No merged universal library or new saved resource is justified.

## 4. Next product-depth candidate: apply a team view from a service context

**Task:** “Our team already defined the useful view for this service; show me that
without rebuilding it from raw fields.”

Existing authorable templates can bind a destination grouping in the saved-view
catalog, and service overview Customize already stages current scope into the
population workspace. Source does not show a direct service-context action for
applicable team templates. Before implementing anything, demonstrate the smallest
contextual bridge using those existing resources. Preserve the service's checked
scope; a saved template is presentation intent, not authority to substitute its
specimen service/window or to execute automatically.

This is a later candidate after the three concrete cuts, requiring an applicability
and discovery contract. No whole-screen WYSIWYG, contributed JavaScript, new view
store, automatic background dashboard reads or access-control promise is selected.

## Remove and consolidate outdated planning

- Mark 347's fresh-pair/service-inventory/typed-package gaps delivered after their
  own final gates; do not keep those historical proposals as parallel work queues.
- Retire scalar-only package UI assumptions and old Use/Explore-means-Run test/docs
  expectations; Stage → explicit Run is now the active contract across consumers.
- Keep proposal 260/checkpoint 274 as dated design background. They must not imply
  that reusable declarations are still wholly missing or gate all product work on
  converting every native presenter/adding Plotly.
- Keep measured 32,000-element/byte limits and arbitrary mid-string caret behavior
  honest, but do not make further facet optimization the default next product task.
- Do not introduce a universal scope manager, store replacement, library merger or
  generic compatibility layer to solve these bounded source/owner gaps.

Recommended finite cadence: distributed continuation breadth → current RPC depth
→ typed service reuse consolidation. Each uses an actual entry-to-return journey,
current desktop/narrow frames, scope/source/ownership checks and appropriate model
negatives before the next cut. The team-template bridge remains a separately
contracted candidate, not an automatically started fourth implementation.
