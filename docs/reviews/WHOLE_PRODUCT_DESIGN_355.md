# Whole-product design/product checkpoint — 355

Proposal only. 354 source/native gates and actual-frame acceptance remain with
their owners. This review starts no implementation and changes no active roadmap.

## Product essence and what is now useful

Goo should make ordinary telemetry immediately explorable: see current events,
isolate a population, follow reported relationships, preserve what was observed
and reuse the useful definition. Manifests strengthen this loop but are not its
entry requirement. Exact scope, uncertain coverage and independent clocks should
travel with the data while the main interface emphasizes useful observations.

Recent work supports this purpose rather than adding disconnected demos: 350
makes typed-scope package authoring usable with Stage → explicit Run; 352–353 make
distributed continuation useful under those policies, with exact versus wider
populations distinct. Service-scoped inventory and count/share explanations fill
real everyday investigation gaps. 354 targets a useful reliability gap: retry one
failed overview widget while healthy observations keep their actual clocks.

The shared passive component/data model is a sound foundation: display kinds
consume supplied exact values and certainty, application owners retain IO/navigation,
and saved views store intent separately from immutable observation. The next work
should expose that foundation to teams and current OTel users, not add a generic
chart vendor, universal state manager or another catalog.

## 1. Breadth: use a team view from the service already under investigation

**Task:** “Our team has a useful HTTP/database/messaging view; apply it here.”

Authorable templates, checked expansion and saved-view inspection/application
already exist in `ui/population-workspace.mjs`. Service widgets already Customize
into that population using a fixed checked destination question. There is no clear
direct service-context bridge to a relevant team-authored template. Reuse those
existing resources rather than invent a dashboard registry or WYSIWYG editor.

Propose a contextual saved-template choice from the existing widget Customize/reuse
flow. Show only admitted applicability, not heuristic claims that a template is
safe for a service. Expand against the actual destination scope/grouping, preview
compatibility, apply configuration locally and require explicit Run. The template's
specimen environment/service/window must never replace the user's investigation.

Acceptance: genuine service overview → applicable saved template → checked preview
→ local Apply → explicit Run → Back; save/reopen preserves the authored declaration.
Include wrong-profile/missing-grouping/typed-policy rejection and a saved specimen
for another service. Metadata inspection/application causes no telemetry reads.
Stop at one supported record/aggregate profile; no native fleet reducer, arbitrary
JavaScript, new kind runtime or broad team access-control promise.

## 2. Depth: one current OTel incoming RPC profile

**Task:** “My service emits current RPC conventions; show the relevant defaults.”

The implemented RPC overview is explicitly legacy `rpc.system`/`rpc.method` with
its named ruleset. Current-convention RPC is still deferred in automatic-dashboard
docs. Research and pin the applicable current OTel convention before implementing
a separate exact profile; do not silently union aliases or call legacy data
current. Reuse automatic candidate selection, explicit Apply, existing duration/
status charts and supporting-record continuations.

Acceptance needs current/legacy/mixed records, correct reported role/presence rules,
exact instrument units, native-only candidates, bounded-page hint uncertainty and
empty results without hidden broadening. Recorded span Error is not a protocol
outcome policy. Stop at one declared profile, not an entire RED/USE/Kubernetes/
broker dashboard portfolio. No new query engine or inference framework is needed.

## 3. Consolidate: put applied package evidence ahead of authoring controls

**Task:** “I ran a reusable question; show its evidence, and let me edit when needed.”

350's actual desktop/narrow frames show a correct Applied scope followed by package
binding, service/duration shortcuts, suggested breakdowns and filter editor before
the result. This is coherent for authoring but weak for reading the saved question's
answer. Source already has `activity-analysis` read-first presentation and explicit
Edit analysis controls, while ordinary package staging returns to the full query
workbench. Saved/population canvases are already data-first; do not create a third
mode or owner.

Propose a bounded shared read-versus-authoring presentation for ordinary applied
package questions, reusing existing scope/status and edit affordances. Show compact
current scope plus evidence before expanded authoring controls. Editing must retain
unapplied predicates and invalidate stale result authority under the existing
session; collapse cannot hide invalid drafts or silently apply them. Stage remains
explicitly not-yet-run, and Run/Use fresh window keep distinct fixed-time meaning.

Acceptance: matched before/after scroll-zero 1280×1000 and 390×844 journeys from
saved package Stage → Run → inspect record → Edit → draft → return. Measure actual
first evidence position and visible control count; no universal above-fold promise
without frames. Prove unchanged query/source budgets, typed policy, receipts, drafts,
Back focus and keyboard reachability. This is a meaningful presentation/ownership
consolidation, not an endless microcopy pass or wholesale rewrite of exploration.

If architecture finds the service-profile facts duplicated across Go planning and
JavaScript eligibility/presentation, a small internal shared-descriptor/generated-
hint cleanup can accompany the RPC cut. It must preserve Go's population/native
query authority and needs its own drift check; a universal registry/DSL is not
justified. Do not substitute that cleanup for the visible workflow outcome.

## Keep the backlog honest

- Close 351's typed distributed continuation and service-library reuse proposals
  after 352/353 validation; do not keep their old unavailable copy as active scope.
- Keep 354 failed-widget recovery as current work until its independent receipts,
  queue, focus and actual frames pass; a green HTTP request alone is insufficient.
- Preserve exact/wider/trace-context distinctions. Shared components must not erase
  the population model to make all screens look alike.
- Do not reopen facet setter/Find work by default. The approximately 32,000-element
  paired tree remains a known performance limit; another rendering change requires
  a new measured user task and truthful CPU-versus-paint/wall results.
- Large platform dashboards, full WYSIWYG, reviewed training labels/datasets,
  multiplayer investigations and operational hardening remain separately contracted
  initiatives. Existing partial implementations are not promises of those products.

Recommend the finite breadth → RPC depth → applied-evidence consolidation sequence,
with architecture/planner reconciling overlap before adoption. Review the whole
product after those three outcomes rather than extending a maintenance-only queue.
