relationships/supporting signals → preserved evidence and reusable definitions.
The grammar's value is keeping the same scope/data/uncertainty meaningful across
these steps, with passive reusable displays and application-owned acquisition.

356 connects team-authored templates to actual service evidence without importing
the specimen's service/window. 357 adds a pinned current RPC population beside the
explicit older interpretation. 358 makes fixed questions read-first while retaining
Edit and forcing dirty/invalid controls visible. Actual matched charts move up
431 px desktop and 890 px narrow but remain below the fold. That is real bounded
progress, not a reason to declare compactness solved or automatically start another
CSS loop. Current 115a/115b Activity regression frames were also viewed at original
detail: staged Run analysis and applied Rerun fixed window remain truthful, with
readable fixed scope and actual log evidence; no new image-quality issue is found.

The product already has automatic service profiles, runtime/host resource views,
pod/container discovery and resource/state/history slices, trace timing/breakdown,
visual population selection, count/share explanation, reusable compositions and
typed package authoring. Do not list these as wholly missing. Broad Kubernetes/

## 1. Breadth: inspect preserved spans as a source-free waterfall

**Task:** “I kept the interesting trace fragment; let me inspect what I actually
saved after the source changed or expired.”

`ui/saved-records.mjs` renders preserved span rows as a table; trace examples and
Expand trace invoke `records.openTrace`, which performs fresh source reads.
`KNOWN_ISSUES.md` explicitly says no stored-waterfall UI exists. Goo already has a
passive supplied-page waterfall kind, timing diagnostics and original-row actions.
This is a product connection gap, not a missing rendering engine or storage system.

Offer a contextual Table/Waterfall representation over the currently supplied
saved span page. Label it captured fragment/page; keep the immutable capture read
clock, retained/paged limits and exact record positions. Missing parents, invalid
IDs, duplicate/ambiguous ownership and incomplete timing remain diagnostic. No
source read, fresh linked-log acquisition or complete-trace claim follows from
switching representation. Expand trace remains a separate clearly fresh action.

Acceptance: capture a real multi-service span fragment, reopen without telemetry,
switch to waterfall, inspect/select the exact stored row, return to the same page,
and deliberately expand fresh context as a separate optional step. Include limited
capture/page, duplicate IDs, zero versus missing durations and source-unavailable
reopen. Native source budgets prove the representation switch is local; actual
frames show frozen origin and fresh expansion clearly separated.

## 2. Depth: compare two retained trace pages as human-comparable evidence

**Task:** “How does this preserved slow/error fragment differ from my reference?”

`TRACE_COMPARISON.md` already defines a Go/JavaScript supplied-page comparison,
exact nullable service/operation groups, signed changes and honest one-sided/unknown
semantics. Use it for two deliberately chosen retained pages if existing custody
can supply their exact rows. Do not create a complete-trace snapshot format or
align separate invocations by IDs as if they were the same event.

Make the reference choice explicit and show both capture/page identities and clocks.
Reuse aligned shared scales and exact counts/inclusive durations; an absent group
on a page is not zero work in the full trace. Unique-label matches are descriptive
alignment candidates, not causality. Keep outside-observed-children measures named
honestly, not CPU/self/critical-path time.

Acceptance: two different captures/windows, literal/missing/empty group labels,
one-sided groups, unknown timing and a bounded page. Choose reference, compare,
inspect either exact stored side and Back with zero telemetry reads. If the current
custody API cannot provide those pages without a new store or source lookup, close
that prerequisite explicitly and keep this cut bounded rather than inventing data.
Stop at existing page comparison; no fleet tracing/statistical cause engine.

## 3. Consolidate: current RPC capability parity across service and measurement views

**Task:** “The service page recognizes this RPC duration instrument; why does its
measurement inspector treat it as generic?”

Architecture identifies a concrete cross-surface gap, confirmed in source:
`exploration/dashboard.go` recognizes current `rpc.server.call.duration` histogram
seconds under the pinned 357 profile, while
`measurements/instrument_capabilities.go` curates HTTP, database-pool and messaging
but has no current RPC capability. This is more useful finite consolidation than
selecting another facet optimization merely because a large DOM exists.

Add the matching checked capability using existing descriptors/presenters. Preserve
exact name/kind/unit/temporality and stream identity, and distinguish recognized
shape, observed attribute coverage and actual semantic-convention verification.
The same instrument should explain the same prerequisites and supported actions
from Services, Measurements and saved contexts. Do not claim all required metric
attributes/values from metadata or upgrade generic eligibility into conformance.

Acceptance: service → exact native instrument → existing capability inspector →
explicit measurement preview → stored/reopened evidence, plus wrong name/unit/kind,
missing dimensions and bounded/omitted streams. Keep v1.45.0 current RPC and legacy
millisecond profiles independent. Reuse current source/renderers, not a universal
profile registry or new grammar. Generated/API/native checks should catch label/
eligibility drift between the existing entry points.

### Large facets remain a conditional measured candidate

The roughly 32,000-element paired tree remains a real structural limit after
343/346, but no new responsive-paint claim follows from earlier five-build CPU
figures; wall results were mixed. Before another change, measure a current actual
mount/search/action/Back task under full admitted long labels. If materially slow,
consider bounded local presentation while searching the whole set and preserving
exact counts, global scales, missing/empty values, row identity and keyboard actions.
No source paging API, general virtualizer or cache authority is presumed. If that
baseline is responsive, do not add speculative machinery. This stays outside the
selected next three outcomes.

## Valuable later candidates, each requiring its own contract

- **Metric exemplars to representative traces:** explicitly unsupported today and
  useful for native-to-record investigation. This needs actual exporter/source
  exemplar fields, identity/time admission and truthful retained custody. A native
  histogram bucket alone does not identify contributing traces.
- **One queue/broker backlog family:** requires a pinned real exporter/instrument,
  queue/broker identity and actual OTLP fixture. Processing spans/duration cannot
  establish queue depth, oldest-work age, capacity or broker health. Existing
  host/Kubernetes resource work is not missing merely because this family is absent.
- **Reviewed evidence labels:** existing tags/notes are not training ground truth.
  The cross-product annotation design still proposes task vocabulary, abstention,
  review and pinned dataset export. Start a concrete reviewed-evidence task before
  active learning, automatic labels or another store.

## Stop outdated queues and protect the pit of success

Mark 355's template bridge/current RPC/read/Edit tasks delivered after their own
validation. Keep 260/274 grammar material as historical direction, not a demand to
migrate every presenter or expose Plotly before useful authoring. Prefer exact
profile compatibility refusal to permissive coercion; typed scope is never a display
label to reconstruct. Keep current/frozen/derived/unknown values explicit in every
new representation and preserve original row identity under visual ordering.

Recommend the finite retained-evidence breadth → trace-page comparison depth →
current-RPC capability-parity consolidation sequence. Architecture/planner should
reconcile it against current storage/rendering contracts before adoption. No new
feature starts from this review alone, and no broad platform catalogue or fourth
maintenance extension is automatically queued.
