# Whole-product design/product checkpoint 372

Source-grounded proposal while 372's typed distribution continuation is under
validation. No next feature is adopted here. No tests, vendor survey or production
edits were performed for this review.

## Essence and delivered scope

Goo's useful loop is current telemetry → scope/isolate → follow reported evidence →
retain and reuse. Live logs/spans, visual selection, exact facets, service/resource
presets, error triage, native context and reusable record views already support it.
370 connects typed error groups to checked child questions; 371 adds a genuine
native plotting declaration over one selected export's complete bins. Do not call
these missing or reopen their compatibility decisions. 372 must finish its own
whole-query/Back gates before another sequence begins.

The native grammar pilot deliberately accepts an exact-ID workflow. That is honest
scope, but a second user cannot naturally discover a view without receiving an ID.
Recent actual triage frames also expose a concrete mobile issue: one horizontal
crop shows identities while another shows actions; the user cannot see both together.
These are reusable-product seams, not reasons to add another semantic profile.

## Proposed finite breadth/depth/consolidation outcomes

### Breadth: discover and reuse native views in context

371's server has create/load/reuse operations but no native-view listing. Use the
existing definition-library interaction to browse a bounded metadata page of saved
native histogram configurations at the current validated destination. Show title,
Histogram/Table, exact unit and compatibility; Inspect is source-free, Apply is
explicit and preserves the current whole question before Run/interval selection.

Reuse existing content-addressed storage and library components rather than a new
registry or global view manager. A donor's scope/results never replace destination
policy/window/stream. Unknown metadata/invalid artifacts remain explicit. Stop at
save → second visit/user context → find → Inspect → Apply → explicit Run and select
actual destination interval, with wrong-unit/kind refusal and stale response tests.
Exact IDs remain available for reproducibility, not the only discovery gesture.

### Depth: close one real OTel histogram-input readiness gap

Exponential histograms remain listed as unsupported and there is no exponential
kernel/source path in the inspected metric modules. Modern OTel exporters may emit
this shape; refusing it is preferable to pretending it is an explicit-bucket alias.
Begin a strict accept/defer contract for one actual source/exporter fixture, including
scale/index mapping, positive/negative buckets, zero threshold/count, unit,
temporality, reset/overlap and finite arithmetic limits.

Only implement if the source can retain those facts and the existing typed snapshot
can represent honest evaluation without rebinning, interpolated percentiles or
silent loss. Define exact expected raw facts and compatibility before UI work.
Otherwise publish the readiness refusal and defer; do not make this a fleet
aggregation or complete-OTel project. A broker/exemplar family could replace this
candidate only after its own concrete source/identity prerequisite closes.

### Consolidate: keep group identity with its action on narrow screens

Actual 370 desktop groups are usable, but mobile needs horizontal traversal between
service/type identity and Inspect/Compare links. Use existing shared table/mobile
composition patterns to make one checked service/type row's identity, count and
primary continuation readable together at 390 px, with long/missing/empty labels.
Do not merely pan the documentation screenshot and call the interaction solved.

Scope this to the shared grouped-record presentation and a representative ordinary
and typed triage owner. Preserve native column semantics, exact row action identity,
full counts, keyboard navigation and current leases. No new data acquisition,
responsive table framework or whole-app redesign. Measure actual row/task geometry
and actions before/after, including return focus; retain horizontal inspection for
secondary wide numeric details if needed. Stop when users can confidently act on
the row they are reading, not after a general CSS cleanup list.

## Risks and reconciliation

The histogram-input candidate is a readiness gate, not promised delivery; a stale
limitation alone is insufficient proof. Native view listing needs bounded metadata
and authority, not unbounded directory scans or invented current consensus. Mobile
changes must reuse shared presentation without hiding meaningful uncertainty or
turning mounted rows into population totals. Review-task enumeration, alerts,
exemplars and broker health retain their separate contracts; do not resurrect old
queues wholesale. Planner/architecture should reconcile these candidates with
actual source feasibility after 372 acceptance, then choose one finite sequence.
