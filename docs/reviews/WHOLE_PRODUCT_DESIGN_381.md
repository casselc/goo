# Whole-product product/design checkpoint — 381

Proposal for root/planner reconciliation after 381 acceptance. This review read
current source/contracts and the 379/380 original screenshots. It ran no browser,
model or test campaign and makes no new vendor-parity claim. It owns only this
review; the proposed sequence below is not another adopted queue.

## Product direction and what is already present

Goo's central loop is **see current telemetry → isolate a population → follow
supporting evidence → preserve or reuse the question and its meaning**. Ordinary
OTel is the starting point; manifests, numeric declarations and authored grammar
are progressive tools. The interface should keep data and its relevant actions
ahead of custody details and configuration.

The repository now implements substantially more than an initial demo: Activity
logs/spans, exact filters and field lookup, time selection, held record selection
and Keep, contextual numeric plots, log patterns, error triage, population and
baseline comparisons, trace/waterfall inspection, automatic service/resource
profiles, immutable captures, reusable compositions/templates and reviewed
captured examples. These are not missing categories to recreate.

379 closes a real entry gap: exponential-only emitters can be found in normal
Services with fixed UTC/namespace scope, while their instruments remain honestly
unsupported. The inspected desktop frame has readable compact native table
headers, stacked service identity and one short action. 380 connects reported
exemplars to immutable Saved evidence without inventing a live adapter. The
retained capture/export/sample citation and local Back make that a useful deeper
investigation, not another isolated chart. 381 should finish its bounded protocol
consolidation before another native family or local guard campaign is scheduled.

## Source-confirmed reachability gap: reuse review vocabularies naturally

`ui/capture-record-review.mjs` offers **Load task** using an exact 64-character ID,
or **Declare a task**. `cmd/goo/capture_reviews_http.go` has task creation and
exact-ID reads, but no bounded task discovery endpoint. The implemented review UI
therefore requires an investigator to carry an ID between records before reusing
the same vocabulary. It is easy to declare another near-duplicate task instead.

This is a missing entry into an existing capability, not a proposal to build a
labeling application or add another top-level destination. A compact task chooser
inside **Review example** should show a bounded searchable page of immutable task
titles/names and label previews, retain exact revision IDs, and require an explicit
selection. Exact-ID loading remains a useful advanced path. Empty discovery,
corrupt/unreadable metadata and partial/bounded results must stay distinct.
Browsing must not resolve a record again, query telemetry or create a task.

## Source-confirmed depth gap: the live-first Keep path cannot use review

The natural Activity gesture is Select → **Keep selected** → inspect the exact
kept observation. `ui/kept-saved.mjs` already preserves the trusted occurrence,
selector, source window and keep clock and can stage trace or surrounding-log
questions. It does not mount the existing review interaction. The review mount is
in `ui/saved-records.mjs`; backend `workbench/capture_review.go:evidenceFrom`
requires an `explore` capture and `CaptureRecordRef{captureId,index}`.

A user should not have to perform a fresh full-question capture just to review the
exact item they already kept. A bounded next depth item is **review one kept log
or span**, after the task chooser is useful. This requires an honest disjoint kept
occurrence/evidence contract verified against its immutable receipt; never fake an
Explore capture, source read, aggregate population or capture index. Preserve
source observation time and keep custody time separately, duplicate occurrences,
explicit uncertain/abstain judgments and historical pin semantics. No inferred
negative labels, automatic trace-wide labels or current-consensus claim follows.
If architecture cannot close that contract within one bounded cut, defer it
explicitly rather than smuggling a second evidence type through the old shape.

## Whole-product presentation debt still affects the core loop

The inspected `380-saved-exemplar-trace.png` is an honest fresh two-span result
with a clear Saved-origin return bar. Yet a 1280×1000 frame shows controls, a large
applied-scope card, trace examples, a duplicated count, a selection disclosure and
deployment context before any actual record row. This agrees with the earlier
359 finding: the read-first layout improved substantially, but actual data still
lands below the fold. It is not evidence that Activity entry itself has regressed.

The next consolidation should address this structurally across fixed ordinary
record results and their Saved/Activity continuations, not add another local
spacing patch. Keep one compact applied-scope/count line with expandable exact
scope/read facts, show the actual record page or explicitly chosen primary chart
next, and move secondary examples, deployment context and selection instructions
to contextual disclosures. Preserve the origin bar and one Run/Edit/Preserve action
row. Dirty or invalid drafts must still force the editor visible; a result must
never appear to use unapplied filters. Use current shared table/list/waterfall,
evidence-summary and disclosure components without a new dashboard manager.

Acceptance should be matched actual frames showing at least the first record or
primary visual with its applied scope on desktop and narrow viewports, plus
keyboard/focus and child-return checks. Measure inside actual scroll containers.
Do not call this complete from fewer DOM nodes, a small pixel gain or actor DOM
completion alone. The source query, counts, immutable origin and independent read
clocks remain unchanged.

## Proposed finite sequence

1. **Breadth — choose an existing review task.** Bounded metadata discovery and a
   contextual chooser in the already delivered review inspector. Validate reuse
   over several captured records without pasted IDs, telemetry reads or duplicate
   task creation. This makes existing labels useful across investigations.
2. **Depth — review one exact kept observation.** Reuse that chooser and the
   current immutable decision/pin workflow with a separately verified kept target.
   Validate source-free reopen, correction/withdrawal, repeated records and
   historical export; no generic population labeling or new identity engine.
3. **Consolidate — put fixed-result data ahead of secondary chrome.** One bounded
   common layout cut over actual fixed records and retained continuations, with
   the matched-frame and semantic acceptance above. Reconcile stale gap docs in
   the same cut; do not extend it into a new component architecture.

Root should reconcile this with the architecture review and adopt only one
finite sequence after 381. There is no need to maintain old prerelease formats,
but current features must not be accidentally removed merely to simplify a type.

## Other worthwhile candidates, not parallel prerequisites

Log-pattern exploration already supports exact count/share, unclassified buckets,
local search/sort, time comparisons and saved scope/YAML. However,
`ui/view-declaration.mjs:eligible` and `workbench/view_declarations.go` explicitly
exclude `column:body_pattern_v1` from the ordinary reusable bar/table declaration.
A checked log-pattern-v1 display profile would connect a useful general log
workflow to the grammar: canonical identity stays distinct from the readable
inferred label, all groups retain full-population denominators and unclassified
coverage, and kind switching/Apply remain source-free. This is a concrete future
grammar-coverage candidate, not permission for endless presenter conversion or a
prerequisite for the sequence above. Do not propose log patterns or time comparison
as entirely missing, or add an opaque clustering/causal algorithm.

Team-contributed broader kinds, a visual grammar editor, collaborative presence,
production tenancy and warehouse lowering remain wider initiatives. None is a
prerequisite for these existing-loop gaps. General exponential evaluation remains
blocked by its source/mathematical contract; observed inventory is not authority
to calculate it. Service exemplar adoption remains explicitly separate from the
new Saved capability.
